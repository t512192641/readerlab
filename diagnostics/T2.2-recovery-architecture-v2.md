# T2.2 版本化恢复／复考架构 v2

## 1. 本架构的结论、范围与效力

### 1.1 共同上游缺口

F-01 至 F-05 不是五处可以分别修补的文字缺陷。它们共同来自一个更上游的架构缺口：
v1 定义了 adapter、夹具、packet、brief、answers 和 baseline 等**资格数据面**，却没有
定义拥有下列责任的**恢复控制面**：

1. 登记一次不可混用的恢复 attempt；
2. 在现行路线和验证器中建立合法、闭合的任务入口；
3. 规定每个产物的唯一写者、最终字节、独立审查和发布条件；
4. 根据合法夹具编译精确实验矩阵、调用路径和分阶段授权预算；
5. 先由技术侧完成 census，再把真实缺口编译成产品负责人可以逐项回答的问题；
6. 把经独立后置审查的 v2 `PASS` baseline 提升为 M2 active evidence，同时永久保留
   v1 `FAIL` 历史。

五项失败在同一条缺失的生命周期上分别表现为：F-01 是合法入口断裂，F-02 是晋级出口
断裂，F-03 是中间发布链断裂，F-04 是实验编译器缺失，F-05 是产品请求编译器缺失。
因此 v2 以一个单向、版本化的恢复控制面同时关闭五项失败，不把它们拆成互不约束的
局部补丁。

### 1.2 本文件现在做什么

本文件只新增技术架构，并把未来路线集成、拆卡、夹具准备、对照、复考和 M2 接线定义到
无需执行会话自行补充架构的粒度。本文件：

- 不修改任何现有文件；
- 不读取或授权当前会话读取 `GOLD-STANDARDS.md` 或 `examples/`；
- 不创建任务卡、adapter、夹具、packet、答案、baseline 或 M2 receipt；
- 不调用模型，不授予任何未来模型、reasoning effort、调用数或费用；
- 不请求产品负责人现在补材料、补判词或作产品决定；
- 不把架构 `frozen`、前置审查 `PASS` 或机械验证偷换成裁判资格通过。

本文件从第一次提交起即为最终字节。后续审查者只读本文件并另写 review；不得在 review
后修改本文件。若 v2 前置审查为 `FAIL`，保留本文件及其 review，另建 v3，不原位修订。
该 review 的唯一允许写入路径固定为
`diagnostics/T2.2-recovery-architecture-v2-preflight-review.md`；review 必须绑定本
文件的实际 commit 和 SHA-256。

### 1.3 后续动作仍需各自授权

本架构设计中的下列动作都不是本文件自动授予的权限：

- 修改路线图、验证器、现有任务卡、README 或 manifest；
- 创建恢复任务卡；
- 读取金标、样张或产品提供的材料；
- 记录产品授权或产品判词；
- 发起任何模型调用；
- 创建 M2 receipt 或进入阶段 3。

它们必须在各自未来任务中获得当时所需的精确权限。技术设计已确定不等于外部或长期
状态修改已获授权。

## 3. 恢复控制面的状态机

### 3.1 单向状态

恢复 attempt 只允许按下列顺序前进：

| 状态 | 进入证据 | 下一步 |
|---|---|---|
| `A0_ARCHITECTURE_FROZEN` | 本 v2 文件有独立 commit 与 SHA-256 | 独立 v2 前置审查 |
| `A1_ARCHITECTURE_RELEASED` | v2 前置审查文件为 `PASS` 并绑定本文件 commit/hash | C0 控制面集成 |
| `A2_CONTROL_PLANE_INTEGRATED` | C0 精确改动通过验证，恢复卡集合仍为空 | 原子注册全部恢复卡 |
| `A3_TASKS_REGISTERED` | 21 张精确任务卡一次性注册且验证通过 | `T2.2-R01` |
| `A4_ADAPTER_RELEASED` | R01 subject + R02 `PASS` review | R03 technical census |
| `A5_ATTEMPT_REGISTERED` | R03 census/gap 经 R04 `PASS` 后，所需产品输入已到位，R05 admission/attempt manifest/package 已冻结 | R06 独立复核 |
| `A6_PACKAGE_RELEASED` | R06 对 R03—R05 全部准备 subject 给出 `PASS` review | 对照控制阶段 |
| `A7_CONTROL_RELEASED` | R10 为 `control-result: PASS` 且 R11 为 `review-result: PASS` | 对照诊断阶段 |
| `A8_CONTRAST_RELEASED` | R14 诊断答案、R15 总结果及 R16 `PASS` review | 正式复考 |
| `A9_RETEST_FROZEN` | R19 答案与 R20 baseline 已冻结 | R21 独立后置审查 |
| `A10_QUALIFICATION_RELEASED` | baseline 为 `PASS` 且 R21 review 为 `PASS` | 总控另开 M2 gate |
| `A11_M2_ACTIVE` | M2 receipt 精确绑定 v2 active evidence 与 v1 history | 才可进入阶段 3 |

任一状态只能读取前序状态的已发布证据，不能读取未来产物。任一 subject 审查失败、hash
不一致、白名单越界、模型授权缺失或 hard gate 失败，均停止在当前 attempt；不得倒退
修改 subject 后沿用原 review，不得跳过状态，也不得借 M2 反向证明任何资格产物。

## 4. C0：任何恢复任务前的控制面集成

### 4.1 C0 的身份

C0 是一次由总控执行、未来另行明确授权的**控制面集成**，不是恢复执行 Agent，也不是
模型任务。其依据是本架构及其独立 `PASS` review。C0 必须先于任何恢复任务卡、金标或
样张读取、产品请求、夹具准备和模型调用。

这里有且只有一个 bootstrap seam：v2 架构前置审查是用户以完整 prompt 直接启动的
治理审查；C0 与随后 21 卡的原子注册由同一个主线程总控在另获明确授权后亲自执行，
不派发给 execution Agent。现行路线已经把日常拆卡、任务卡创建、技术核验和集成归给
总控；“任务卡是唯一指令源”从第一个被派发的 recovery execution Agent R01 开始适用。
因此：

- 前置审查只写第 1.2 节固定 review 路径；
- C0 只写第 4.2 节固定现有路径；
- card registration 只写第 4.5 节 21 个固定路径；
- 三者都由用户 prompt + 本架构固定 scope 驱动，不创建子 execution 会话；
- 第一个被派发的会话必须是已经有合法卡、且 validator 通过后的 R01。

C0 必须把这条 controller-only bootstrap seam 逐字写入路线图；不得把它泛化为未来
执行任务可以跳过 taskcard 的例外。若未来授权要求把 C0 或 card registration 派发给
另一个 Agent，则必须先停止，因为现行入口仍不合法。

### 4.5 原子卡注册

commit 中一次性新增全部 21 张任务卡；禁止只注册一部分后派发。每张卡必须逐文件列出
允许读取、允许写入、上游 subject/review hash gate、blocker 路径和四层完成状态。

卡注册 commit 只新增：
`taskcards/T2.2-R01.md` 至 `taskcards/T2.2-R21.md`。注册后先再次通过验证，才可派发
R01。卡片路径已经由本架构全部固定；模型配置和产品答案仍作为未来 gate 输入，不通过
修改任务卡来补写。

### 5.2 提交与冻结协议

每张卡恰好一个本地 commit。subject writer 在自己的 commit 中直接写
`status: frozen` 的最终字节；不存在 `draft → review → 原位改 frozen` 的状态转换。

“frozen”只表示字节不可变，不表示 `PASS`、已发布或可供下游消费。发布必须同时具备：

1. subject writer commit；
2. subject 文件逐字节 SHA-256；
3. 后续独立 reviewer commit；
4. review 文件逐项绑定 subject commit/hash 并给出 `PASS`。

reviewer 不修改 subject。若 review 为 `FAIL`，subject 与 review 都保留；同一文件不能
修后重审，必须启用新版本和新 attempt。SHA-256 对原始文件字节计算，不换行归一化、
不 trim、不重排 Markdown。

每个独立 review 必须含且只含一个可机械读取的
`review-result: PASS|FAIL` 和一个 `subjects-unchanged-since-commit: yes|no`，并以逐
路径表列出每个 subject 的 owner task、相对路径、40 位 lowercase subject commit 和
64 位 lowercase SHA-256。reviewer 必须逐 commit 核对 diff 只含对应卡声明的 subject，
且当前 subject bytes 与该 commit 一致；任一不满足只能 `FAIL`。review 不写自身 hash，
消费者重算 review 的实际 hash。

每个文件只能引用已经存在的上游路径和 hash：

- subject 不写自身 hash；
- review 可以绑定 subject，但 subject 不预写未来 review；
- receipt 不写自身 hash；
- 下游在读取时同时重算 subject 与 review 的实际 hash；
- key 可以绑定 packet，packet 禁止读取或绑定 key；
- judge-visible brief 不绑定某一个 packet；隐藏 call manifest 绑定实际 brief/packet；
- baseline 可以绑定全部已冻结输入、答案和 review；未来 M2 receipt 再绑定 baseline。

### 5.3 阻塞协议

任一任务遇到不满足的前置条件，只能写自己已注册的
`taskcards/T2.2-Rxx-BLOCKER.md` 并停止。blocker 必须区分：

- `technical`: hash、路径、审查、解析、对象准入或实验条件不满足；
- `product`: 只有 R03 形成的精确材料／scope 请求尚未得到产品答复；
- `authorization`: 模型、调用数、reasoning effort 或未来写入尚未获当时授权；
- `owner-conflict`: owner 文件冲突，不能自行选择。

blocker 不能授权绕过 gate。解除 blocker 不允许编辑已经 frozen 的 subject；需要新
attempt 时由总控另行设计和授权。唯一例外是 R03 的精确 product-request blocker：
它只表示等待已经 R04 独立审查通过的产品输入，可由 R05 的 frozen resolution 逐
request-id 关闭，但 R03 census、gap 和 blocker 本身仍不修改。其他 recovery blocker 不能在 A01 内
被后续任务宣称关闭。

## 6. Adapter：三个对象域与资格语义

`blind-packet-v2` 是 14 个中性对象的 canonical catalog。正式 judge 不读取整包，只读
与自己中性 ID 对应的一个 retest packet。每个 retest packet 的候选和完整
`SOURCE-CONTEXT` bytes 必须与 catalog 对应对象逐字节一致。

### 8.2 中性 ID 与 sentinel 的确定性选择

R05 使用 attempt salt 对 14 个 selected candidate ID 计算
`SHA-256(<salt-bytes> || <candidate-id-utf8>)`，按 digest 升序赋值 `Q01`—`Q14`。
若 digest 碰撞即 technical blocker，不自行加盐。packet、key 和正式答案路径都使用该
冻结顺序。

对照 sentinel 只按冻结 census 次序选择：

- `P`：selected positive 中 candidate ID 最小者；
- `N1`：selected negative 中 candidate ID 最小者；

固定矩阵只使用 P/N1。不得根据模型结果、措辞难度或预计成绩选择 sentinel。

### 8.3 固定实验臂

所有臂使用同一模型、reasoning effort、T1.8、adapter、输出 schema、无重试规则和
fresh isolation。arms 对 judge 隐藏。

| 臂 | 输入 | 相对控制的唯一变化 | 允许得出的最窄结论 |
|---|---|---|---|
| C | P、N1；每次单对象、完整上下文、完整 procedure | 无 | 当前模型在这些 sentinel 的保守条件下是否 2/2 稳定 |
| B | 与 C 完全相同的 P/N1 packet；使用 no-differential brief | 只删除 brief 中精确的 `DIFFERENTIAL-PROCEDURE` block | 结果差异与该 procedure block 在这些 sentinel 上有关 |
| E | P/N1 候选 bytes、ID、brief 都与 C 相同；`SOURCE-CONTEXT` payload 为零 bytes | 只移除原文上下文 bytes | 结果差异与上下文缺失在这些 sentinel 上有关 |
| G | 两个 canonical atom 保持两个独立 judgment object，分别反转顺序 | 只从单对象调用改为双对象 batch，并以反序检测位置效应 | 是否出现本地 batch／顺序敏感 |

完整 brief 必须以字面量标记一个
`DIFFERENTIAL-PROCEDURE` block。
`diagnostics/T2.2-judge-brief-variant-v1-02.md` 必须等于完整 brief 删除该完整 block
（含边界标记）后的原始 bytes；其余 bytes 不得变化，不做空白归一化。不得把 B 命名
或解释为 `legacy`。

E packet 保留原 packet 的字段、分隔符、ID 和候选 bytes，只让
`SOURCE-CONTEXT` 字段的 payload 长度为 0。G 的两个 order packet 复用 canonical atom
bytes，但各自为独立文件。G 中每个对象分别输出 disposition。

O 组成臂从 v2 可执行矩阵中移除：它不是正式复考配置的选择条件，又会新增 N2、对象
组成和四次调用分支。v2 对“合并对象是否是 v1 失败原因”保持 `unknown`，不为回答这个
非阻塞问题增加产品请求、文件或调用。

隐藏 contrast key 必须冻结以下唯一映射；R05 不得自行换号：

| 中性 packet | scoring-side 含义 | judge-visible bytes |
|---|---|---|
| `T2.2-contrast-packet-v1-01.md` | C/B 的 P | P canonical atom + full context |
| `T2.2-contrast-packet-v1-02.md` | C/B 的 N1 | N1 canonical atom + full context |
| `T2.2-contrast-packet-v1-03.md` | E 的 P | 与 01 相同，只有 context payload 为零 bytes |
| `T2.2-contrast-packet-v1-04.md` | E 的 N1 | 与 02 相同，只有 context payload 为零 bytes |

| `T2.2-contrast-packet-v1-06.md` | G order 2 | 02 与 01 的 atom bytes，两个对象，N1→P |

category、来源或实验目的。brief variant 的文件名只表达中性版本号，不表达被删除
block 的含义。

### 8.5 分阶段授权与停止

R07 只能记录控制阶段 4 次调用的明确授权。R09 完成后，R10 必须写唯一字段
`control-result: PASS|FAIL` 并确认：

- P 两次均为 `放行`；
- N1 两次均为 `拦截`；

任一不满足即控制 `FAIL`，R11 复核后停止；不得请求剩余诊断调用，也不得用正式 14
对象复考继续试。R11 的 `review-result: PASS` 只表示它正确复核了 R10，不会把
`control-result: FAIL` 提升为通过。只有 R10 `control-result: PASS` 与 R11
`review-result: PASS` 同时成立，R12 才能请求并记录**另一次**精确的 10 次诊断调用
授权。

R07、R12、R17 的 call manifest 都必须含唯一字段：
`attempt-id`、`stage`、`authorization-source`、`authorization-scope`、`model`、
`reasoning-effort`、`call-count`、`no-retry: true`，并逐 call 列出中性 call ID、
brief path/hash、packet path/hash、answer path 和允许输出 schema。authorization
source/scope 必须忠实记录当前任务获得的明确授权，不能引用本架构作为授权来源。
R08、R13、R18 分别机械核对 manifest 的 call-count、逐项路径闭集和输入实际 hash。

R15 对 B/E/G 只作第 8.3 节的局部观察。矛盾保持 `unknown`；不追加样本、不补跑、
不换模型、不把 E/G 当资格证据。对照不“选择模型”：本 attempt 的模型和 reasoning
effort 在三阶段必须相同。若需换模型，建立新 attempt，重新从控制阶段开始。

R16 `PASS` 只证明对照证据与窄结论一致。正式复考配置不由观察臂挑选，始终使用最保守的
C 条件：完整上下文、完整 procedure、单对象、fresh isolated turn。

## 9. 正式复考与答案身份

### 9.1 R17 的精确授权

R17 必须在 R16 `PASS` 后，另行取得 14 次模型调用的明确授权，并冻结：

- 与 R07/R12 完全相同的模型与 reasoning effort；
- 14 个 Q ID 的固定顺序；
- 每次一个 retest packet、完整 brief、T1.8 和 adapter 的实际 SHA-256；
- `diagnostics/T2.2-judge-answer-v2-01.md` 至
  `diagnostics/T2.2-judge-answer-v2-14.md` 的逐项映射；
- 一次调用一个对象、一次机会、无 retry／follow-up；
- judge-visible 白名单与禁止读取清单；
- 总调用数恰为 14。

R18 独立重算所有 input hash、顺序、路径、模型一致性、固定 M14 已完成状态和 R16 review
hash。只有 R18 `PASS`，R19 才可调用。

### 9.2 评分与 hard gate

R19 的 14 个 fresh judge 各自只写一个 frozen answer。R19 主控最后写 frozen index，
逐项绑定 call ID、Q ID、模型、reasoning effort、输入 hashes、answer path 和 answer
hash，不汇总改写答案。

R20 只在 14 个答案和 index 全部冻结后读取 scoring key，机械计算：

- negative：必须 `8/8` 为 `拦截`；
- positive：必须 `3/3` 为 `放行`；
- reference：记录实际 disposition，不参与 hard gate。

任一 hard gate 未满足，baseline 如实为 `FAIL` 并同时写
`taskcards/T2.2-R20-BLOCKER.md`。baseline 无论 `PASS` 或 `FAIL` 都保持
`status: frozen`、`scope: long-term`，绑定本 attempt 从 architecture、adapter、
census、admission、package、三段 call manifest/review、全部 answer/index 到 scoring
key 的完整 hash chain。冻结 baseline 不等于资格已发布。

R21 未参与 adapter、census、package、调用或评分，独立重算全部 hash、14 项顺序、
模型配置、白名单、机械成绩、hard gate 和 v1 历史未变。只有 baseline `PASS` 且 R21
review `PASS`，状态才到 `A10_QUALIFICATION_RELEASED`。

## 10. 产物 DAG、发布边与信息隔离

### 10.1 唯一拓扑

完整依赖只允许：

```text
v2 architecture
  -> architecture preflight PASS
  -> C0
  -> 21 cards
  -> adapter -> adapter review PASS
  -> census/gap -> census review PASS
  -> product input if and only if a reviewed exact gap exists
  -> resolution -> admission -> attempt manifest -> package
  -> preparation/package preflight PASS
  -> control manifest -> input review PASS -> control answers/index
  -> control result -> control postflight PASS
  -> diagnostic manifest -> input review PASS -> diagnostic answers/index
  -> contrast result -> contrast postflight PASS
  -> retest manifest -> input review PASS -> 14 answers/index
  -> baseline -> postflight review PASS
  -> M2 receipt
```

没有从 M2、baseline、结果、答案或 key 指回 packet/brief/census 的写边；没有 reviewer
修改 subject 的边；没有 packet 读取 key 的边；没有正式 judge 读取对照答案的边。

### 10.2 release rule

下游读取一个会影响产品请求、调用或晋级的结果时，必须同时读取并核验该结果的独立
review：

- adapter 消费者绑定 R01 + R02；
- 产品请求绑定 R03 + R04；
- package 是 R05 内部尚未发布的 preparation transaction；唯一外部消费者必须同时绑定
  R03、R04、R05 与 R06；
- stage-B manifest 要求 R10 `control-result: PASS` + R11 `review-result: PASS`；
- retest manifest 绑定 R15 + R16；
- M2 receipt 绑定 R20 + R21。

任何未审 draft、工作区临时文件、聊天摘要、模型自评或只有 subject hash 的文件都不是
release evidence。

### 10.3 scoring／judge 隔离

- Census、admission、key、call manifest、answer index、results、baseline 和 review
  属于 preparation/scoring/review side。
- Judge 只看第 6.2 节白名单。
- Packet 不包含 source path、文件名、positive/negative/reference、产品判词、expected
  disposition、arm 名或其他对象结果。
- Brief 是 packet-neutral；具体 packet/brief 组合由隐藏 call manifest 绑定。
- 对照答案不进入正式复考 judge 上下文；正式答案彼此隔离。
- T2.1、T2.3、v1 answers/baseline/blocker 均不进入任何 v2 judge 上下文。

## 13. 冲突、重复、循环和新不可执行要求检查

### 13.1 已消解的交叉冲突

1. **F-01 与 F-02 的修改面重叠**：两者都需要路线／验证器改动，因此合并成同一个 C0，
   在任何恢复执行前一次完成；不会复考后才发现 M2 无入口。
2. **F-03 与 F-04 的时序冲突**：固定 M14 先由 attempt manifest 冻结，package、三个
   call manifest 和控制结果各自先 commit 后 review；调用不会读取仍会变化的设计。
3. **F-04 与 F-05 的额外诊断冲突**：O/N2 已移出可执行范围；固定 M14 不为非阻塞诊断
   制造产品请求、文件分支或额外预算。
4. **产品答复与 census 冻结冲突**：R03 不被编辑；R04 先独立审查 gap，R05 再以新
   resolution/admission 复核答复，不手改旧行。
5. **route 预接线与未来文件尚不存在**：C0 只声明精确未来路径且保持 M2 不存在；
   validator 只有 receipt 出现时才要求 active 文件齐全，不把路径声明当作通过。
6. **v1 历史与 v2 active 冲突**：路径完全版本化，M2 同时拥有 active 与 history 字段，
   没有覆盖、重命名或“最新文件”选择。
7. **R04 与 R06 的审查重叠**：R04 只在产品接触前证明 census/gap 可提问；R06 在产品
   输入落盘和 package 编译后证明最终调用输入可发布。前者防止错误产品请求，后者防止
   错误模型调用，审查对象和 gate 时点不同，不能互相省略。

### 13.2 无重复 owner

- 产品 owner 只回答材料授权和判词 scope；
- R03 是 census/gap writer；R04 只审 census/gap；
- R05 是产品输入技术记录、resolution、admission、attempt 与 package writer；R06
  只审 R03—R05 release unit；
- R09/R14/R19 judge 各自只写独占答案；
- R10/R15/R20 scoring owner 分别写控制结果、对照结果、baseline；
- R02/R04/R06/R08/R11/R13/R16/R18/R21 reviewer 只写 review；
- 总控只拥有 C0、card registration 和未来 M2 receipt。

同一路径没有两个写者；同一产品问题没有同时向产品和技术侧索取同一个决定。

### 13.3 无循环依赖

- package 不依赖对照结果；对照读取已发布 package；
- formal configuration 不由 E/G 观察臂动态改写；它固定为 C 条件；
- baseline 不依赖 M2；M2 只依赖已审 baseline；
- review 不被 subject 反向绑定；
- product input 不改变已经冻结的候选排序；
- downstream 不通过 alias 反向选择最新版本。

### 13.4 没有新增不可执行要求

- 所有 task ID、subject、review、answer、blocker 和 material slot 均为字面量闭集；
- 固定 M14 的调用公式、packet/brief/answer 映射和预算都可在调用前复算；
- 模型未知不会靠猜测补齐，而在 R07/R12/R17 各自形成精确 authorization gate；
- 产品缺口未知不会提前泛化请求，而由 R03 的固定 schema 编译；
- O/N2 已显式移出，不存在 optional 分支或为其补材料的死路；
- 任一失败都有已注册 blocker 路径，不要求执行会话发明新文件；
- 没有新增 runtime dependency、数据库、schema migration、远端服务或云端写入。
