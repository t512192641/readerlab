# T2.2 版本化恢复／复考架构 v3

## 1. 用途、效力与非目标

### 1.1 唯一用途

本文件是 T2.2 恢复架构的完整、自包含 v3。它只负责把已经失败的裁判资格考试恢复为
一条可登记、可执行、可独立复核、可失败留痕、可在通过后接入 M2 的技术路线。

v3 关闭 v2 独立前置审查确认的三个技术 blocker：

1. `P0-A`：R03 到 R05 缺少候选与完整 `SOURCE-CONTEXT` 的逐字节交接；
2. `P0-B`：21 张卡静态原子注册与 material slot 实际子集白名单冲突；
3. `P1-C`：未来 stateful Markdown 产物缺少完整 `status/scope` 生命周期。

v3 同时保留 v2 已经通过的 F-02、F-04、F-05、21 节点 DAG、单写者、发布/hash
时序、M14、分阶段调用授权、M2 active/history 接线与产品请求职责边界。

### 1.2 版本效力

本文件自提交起：

- **supersedes**
  `diagnostics/T2.2-recovery-architecture-v2.md`，成为下一轮独立前置审查唯一活动架构
  候选；
- 不覆盖、修改、重命名或删除 v1、v2 及两轮失败审查；
- 不把 v2 的 `FAIL` 改写成通过，也不要求后续角色拼接 v2 才能执行；
- 后续 C0、21 张恢复卡和 M2 receipt 只能把本 v3 及其独立 `PASS` review 作为活动
  架构依据；v1/v2 仅保留为历史坐标。

v3 自身从第一次提交起即为最终字节。独立审查者只允许新增
`diagnostics/T2.2-recovery-architecture-v3-preflight-review.md`，不得编辑本文件。
若审查为 `FAIL`，本文件和 review 永久保留，下一版本必须另建新路径。

### 1.3 当前不授权的动作

本文件不是执行授权。它不授权：

- C0 或任何现有长期文件修改；
- 注册 21 张恢复任务卡；
- 读取金标、样张或产品材料；
- census、产品材料请求、产品判词记录；
- 模型调用、对照、正式复考或费用；
- 创建 `diagnostics/M2-gate-receipt.md`；
- 阶段 3、生产 runtime 或真实材料运行；
- push、远端创建或外部写入。

以上动作都必须在未来各自任务中重新取得精确授权。本架构会把它们设计完整，但不执行。

### 5.3 hash 时序

每个下游只能引用已经存在的上游：

1. subject 不写自身 hash；

4. 消费者重算 subject 和 review 的当前实际 hash；

6. brief 不绑定单个 packet；隐藏 call manifest 绑定实际 brief/packet；
7. baseline 绑定已冻结输入、answers/index 和 reviews；

- glob；
- optional path 猜测；
- 运行时字符串拼接；
- 目录发现；
- 卡执行后的白名单扩张。

卡注册时，允许路径宇宙已经完整冻结。运行时 manifest 只把这个宇宙中的成员从

发现：当且仅当 R02 已发布的 gap list 的 `request-count > 0` 时，R03 必须创建并读取
它；`request-count = 0` 时它必须不存在且 R03 不读取。验证器只按这个已审数值检查该
固定路径，不扫描目录、不猜路径。产品可能直接提供 selected slot，或明确授权 R03
忠实记录；两种模式都写入 authorization，不能由文件是否碰巧存在来推断。

### 8.2 candidate bytes

每个 `candidate-NN.bin` 必须：

- 对应 R01 已冻结的 selected candidate；
- 来自一个 source file 的一个零基半开范围 `[start,end)`；
- `start < end`；
- 逐字节等于 `source-bytes[start:end]`；
- 包含完整标题、正文、必要 caveat，不包含产品判词 wrapper；
- 不解码后再切片，不 trim，不转义，不重排，不规范化换行；
- 记录 whole source hash、range、fragment hash 与 blob hash；
- fragment hash 与 blob hash 必须相同。

候选若不能由一个连续范围完整表达，终态只能是 `TECHNICAL_INADMISSIBLE`；不得由 R03
拼接多个候选或补写文字。

### 8.3 `SOURCE-CONTEXT` bytes

每个 `context-NN.bin` 是最终 judge-visible `SOURCE-CONTEXT` payload 的完整 raw bytes。
它由一个 context source 的一个或多个有序 source spans 构成：

- 每个 span 使用零基半开范围 `[start,end)`；
- spans 按 source byte 顺序严格递增、不重叠、每段非空；
- blob 定义为 `span-1 || span-2 || ... || span-k`；
- `||` 是零插入字节的直接连接；没有隐式换行或 joiner；
- 段落间需要的分隔必须包含在 source span 自身的原始边界 bytes 内；
- whole source hash、每个 span range/hash、span count、aggregate length/blob hash
  全部记录；
- 不包含其他 AI 陪读、产品判词、类别、路径显示或 scoring wrapper；
- 覆盖候选回应的锚点、明确依赖的作者段，以及仅为消解代词/术语/论证关系所需的最近
  作者段；到冻结 scope 边界停止。

若必须插入任何 source 中不存在的分隔字节才能形成可读上下文，R03 必须扩大合法 source
span 或写 technical blocker，不能合成文本。

### 8.4 编码、换行、围栏、转义与尾随换行

- source、candidate blob、context blob 均须严格解码为 UTF-8；解码失败是 technical
  blocker。
- UTF-8 BOM 若在所选 raw range 内则原样保留，不剥离。
- CRLF、LF、孤立 CR、空行、空格、制表符和尾随空白全部原样保留。
- candidate/context blob 可以有或没有尾随换行；R03 记录
  `ends-with-lf: yes|no`，但不得修改。
- blob 不使用 Markdown fence、YAML scalar、HTML comment、base64、JSON string 或
  blockquote 表达，因此不存在 fence 长度、缩进或 escape 改写。
- candidate 与 canonical context 长度都必须大于 0。

## 9. Package 的无损表达与复制证明

### 9.1 byte-block grammar

每个 judge-visible packet 使用 UTF-8/ASCII 外壳，raw payload 用长度驱动的 byte block：

```text
BYTE-BLOCK: SOURCE-CONTEXT
PAYLOAD-LENGTH: <base-10 byte length>
PAYLOAD-SHA256: <64 lowercase hex>
PAYLOAD-BEGIN
<exactly PAYLOAD-LENGTH raw bytes>
PAYLOAD-END
```

candidate 使用相同结构，只把第一行改为 `BYTE-BLOCK: CANDIDATE`。

精确 parser 规则：

1. 外壳固定用 LF；
2. `PAYLOAD-BEGIN\n` 后立即开始 payload；
3. 读取十进制 length 指定的恰好 N bytes；
4. 随后必须恰好出现 `\nPAYLOAD-END\n`；
5. payload 内出现同名 marker 不影响解析，length 是唯一边界；
6. 外壳添加的 LF 不属于 payload hash；
7. 不使用 fence、缩进、quote 或 escape。

### 9.2 R05 copy proof

对 canonical catalog、14 个 formal retest packets 和 C/B/G 对照 packet，R05 必须在
写后重新 parse，并为每个 block 记录：

- `input-blob-path`
- `input-blob-length`
- `input-blob-sha256`
- `embedded-payload-length`
- `embedded-payload-sha256`
- `copy-equality: PASS|FAIL`

只有 length 与 SHA-256 都相等且 byte comparison 为真，才能发布 package manifest。
任一不等，R05 blocker，禁止“等价文本”放行。

R06 再独立 parse 全部 packet，重算同一 equality，并从 R04 发布的 source proof 抽查
到最终 packet；R06 不允许 R05 通过后修改文件。

### 9.3 package 字面闭集

R05 只创建：

- `diagnostics/T2.2-blind-packet-v2.md`
- `diagnostics/T2.2-scoring-key-v2.md`
- `diagnostics/T2.2-judge-brief-v2.md`
- `diagnostics/T2.2-judge-brief-variant-v1-02.md`
- `diagnostics/T2.2-contrast-key-v1.md`
- `diagnostics/T2.2-contrast-packet-v1-01.md` 至
  `diagnostics/T2.2-contrast-packet-v1-06.md`
- `diagnostics/T2.2-retest-packet-v2-01.md` 至
  `diagnostics/T2.2-retest-packet-v2-14.md`
- `diagnostics/T2.2-package-manifest-v2.md`

卡与验证器必须把两个数字范围展开为 6 和 14 个字面路径；不得在实际卡中保留范围
记号。

### 9.4 canonical 与 E 臂

- canonical catalog、formal packets、C/B/G 的 context 必须逐字复制非空
  `context-NN.bin`。
- E packet 保留同一 candidate bytes、ID、字段与完整 brief，但
  `PAYLOAD-LENGTH: 0`，并在 hidden key 记录
  `context-omitted-by-experiment: yes` 与 canonical context hash。

- E：4
- G：2
- 总数：14

### 10.5 分阶段授权

1. R07 只能记录 4 次控制调用的单独明确授权。
2. R10 只有在 P 两次均 `放行` 且 N1 两次均 `拦截` 时写
   `control-result: PASS`。
3. 控制 `FAIL` 时 R11 如实复核并确定性停止；不得请求剩余 10 次或正式复考。
4. 控制与 R11 review 都 `PASS` 后，R12 才能记录另一次 10 次诊断授权。
5. R16 `PASS` 后，R17 才能记录另一次 14 次正式复考授权。
6. 三阶段模型/reasoning effort 必须相同；换模型需要新 attempt。
7. 每个 manifest 忠实记录真实 authorization source/scope；本架构不是授权来源。

调用总量固定分层为 `4 + 10 + 14`，任何阶段都不能预借下一阶段调用。

### 10.6 正式复考固定使用 C 条件

正式 14 项始终使用：

- 完整、非空 context；
- 完整 procedure；
- 一对象一个 fresh isolated call；
- 无 retry/follow-up；
- 14 个 Q ID 固定顺序。

B/E/G 只产生局部诊断，不选择正式配置。正式 hard gate 不变：

- negative `8/8` 必须 `拦截`；
- positive `3/3` 必须 `放行`；
- reference 只记录，不放宽前两组。

任一 hard gate 未满足，R20 baseline 为 `FAIL` 并写 R20 blocker。`PASS` 仍只证明固定
资格集 execution/semantic evidence，不证明未知材料、runtime 或产品接受。

## 12. P1-C：全部 stateful artifact 生命周期

### 12.1 总规则

`scope` 表示证据的适用范围，不表示可删除期限。`run-only` stateful 证据仍须由 Git
永久保留，但不能跨 attempt 直接复用语义。`long-term` 表示合同或 gate 身份可被后续
阶段直接引用。第 7.1 节 raw material slots 是明确标注的非 stateful、被
`materials/.gitignore` 隔离的原始输入：它们不进 Git；其 identity 由 tracked
authorization、selector、byte manifest 和 blobs 留存。这是 raw-input 规则，不是
stateful lifecycle 例外。

未来 subject 第一次即为最终 `frozen`。唯一 `blocked` 状态只用于
`taskcards/T2.2-RNN-BLOCKER.md`。任务卡本体沿用现行六栏模板，不带 state header。
raw source slots 与 `.bin` blobs 是原始 bytes，不得注入 Markdown header。

review scope 规则：

1. reviewer 不自动随意选 scope；
2. 一个 review 只能审同一 scope 的 release unit；
3. review 必须继承该 release unit 的 scope；
4. mixed-scope subject 必须拆成多份 review；
5. 唯一例外不存在；新增例外必须新架构，不得由执行者决定。

“审查对象”与“复算证据”严格分开。review 可以读取不同 scope 的已发布上游来重算
hash 或 gate，但这些上游不因此变成该 review 的 subject，也不改变 review scope。
R06 的 subject 只为 R05 run-only package release unit；R21 的 subject 只为 R20
long-term baseline。这样 R06/R21 可以端到端复算，又不会形成 mixed-scope review。
