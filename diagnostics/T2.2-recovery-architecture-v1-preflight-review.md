## 2. 最终结论

**FAIL**

架构正确保留了冻结 T1.8 对真实 B2 验收对象的长期责任，正确隔离了历史资格夹具，
也明确保留 v1 全部失败证据和未来模型调用授权边界。但它目前不能被安全拆成后续任务：
四张建议任务卡会被现行 `validate.py` 确定性拒绝，M2 的活动 v2 baseline 接线仍被留作

这些都是可由技术架构角色修正的问题。现有 owner 文件已经足以完成本次评价，不需要

恢复任务卡、补材料、调用模型、执行对照、复考、创建 M2 receipt 或进入阶段 3。

## 3. 发现列表

### F-01｜P0｜建议任务卡与验证器、现行复合任务规则直接冲突

**证据**

- 架构建议新增四张任务卡：
  `diagnostics/T2.2-recovery-architecture-v1.md:435`、
  `:441`、`:448`、`:453`。
- `validate.py:56-80` 固定 24 个正式 `TASK_IDS`。
- `validate.py:666-683` 只允许固定正式卡、`TEMPLATE.md` 和
  `<固定任务编号>-BLOCKER.md`；其余 `T*.md` 全部记为 unexpected。
- 路线图只允许原 T2.2 是隔离复合任务；其余任务保持单会话：
  `blueprints/EXECUTION-ROADMAP.md:15`、`:23`、`:64`。架构的 16 个鲜会话对照没有
  先取得这条路线例外的版本化接线。

**实际后果**

建议路径任一落盘，`python3 validate.py` 都会失败；16 调用对照也没有合法任务入口。
任务卡是执行 Agent 的唯一指令来源，因此当前架构无法生成下一张既自包含又能通过验证
的恢复任务卡。这是第一步即发生的确定死路。

**最小修正方向**

架构修订必须先明确一个获授权的路线／验证器集成步骤或一个现行验证器可接受的精确
派发形式，并写清其 owner、先后顺序、允许修改范围和机械验收。该集成在任何恢复卡
创建及任何模型调用前必须已经通过；不得把验证器失败留给执行会话临场处理。

### F-02｜P0｜v2 活动 baseline 没有落成可执行的 M2 接线

**证据**

- 路线图固定要求 M2 绑定 `diagnostics/T2.2-judge-baseline.md`：
  `blueprints/EXECUTION-ROADMAP.md:24`、`:108`。
- 该路径已由 v1 永久记录 `FAIL`：
  `diagnostics/T2.2-judge-baseline.md:7-11`。
- 架构只声明未来 v2 baseline 应成为 active evidence，并把路线图／任务卡修改留给
  后续任务：`diagnostics/T2.2-recovery-architecture-v1.md:460-473`。
- R5 仍把“active baseline 版本集成点已解决”列作进入条件，而没有给出负责解决它的
  owner 产物和前置任务：同文件 `:597-607`；该缺口又在 `:680-681` 被明确列为 blocker。

**实际后果**

即使 R0—R4 和 v2 hard gate 全部通过，现行 M2 receipt 仍只能绑定永久失败的 v1 路径；
Route D 会在已消耗材料、对照和复考调用后才停住。失败历史虽未覆盖，但成功证据也无法
进入正式 gate。

**最小修正方向**

架构修订必须在任何恢复执行前定义无歧义的版本选择产物、写 owner、任务顺序和机械
验证：v2 baseline 如何成为 M2 的活动资格证据，v1 baseline／blocker 如何继续作为
失败历史被保留，以及 receipt、路线图、任务卡和验证器分别核对哪些精确路径与 hash。

### F-03｜P1｜adapter、brief 与对照结果的冻结 owner 和 hash 时序不闭合

**证据**

- adapter 被定义为 `draft`，审查后转为 `frozen`，写 owner 是资格合同编制角色，但又
  写成“冻结由前置审查 gate”：
  `diagnostics/T2.2-recovery-architecture-v1.md:434`。
- v2 brief 被列为 frozen，并要求绑定 adapter／packet，却写“前置审查冻结”：
  同文件 `:439-440`。
- R1 的角色必须独立且不参与夹具编制，只有其 review `PASS` 才可请求调用：
  同文件 `:537-552`。
- 对照结果被定义为永久 `draft / long-term`，却直接供正式复考卡选择模型／粒度：
  同文件 `:447-448`、`:558-575`，没有冻结点或 receipt。

**实际后果**

若审查后再把 adapter 从 draft 改为 frozen，文件 hash 会变化，审查所见字节和 brief
绑定字节不再相同；若由审查者修改 adapter／brief，又破坏独立审查角色边界。未冻结的
对照结果继续作为复考配置依据，也无法证明复考消费的是哪一版结论。

**最小修正方向**

架构修订须逐文件指定实际写入者、状态转换者、独立审查者、最终冻结 commit／receipt
和 hash 顺序。独立审查必须检查将被调用的最终字节而不编辑被审输入；对照结果在进入
复考任务前也必须有不可变身份和明确绑定。

### F-04｜P1｜最小对照不能支持其声称的单变量因果结论

**证据**

- 对照声称每个实验臂相对控制臂只有一个差异：
  `diagnostics/T2.2-recovery-architecture-v1.md:351-359`。
- C 要求一正一负分别单对象调用，G 要求把同一正负放进一个 batch；但文件矩阵只给
  一个 control packet，且写明 B、G 复用它：同文件 `:443-446`。若 control packet
  同时含两对象，C 并非单对象上下文；若分成两个 packet，G 又没有复用同一 packet。
- B 只写为未定义边界的 `legacy-style brief`，而所有对照 judge 仍读取拥有处置映射的
  adapter；因此无法确定 B 实际改变的是 brief 表达、操作程序还是处置映射：
  同文件 `:356`，以及 adapter 责任 `:304-325`。
- O 在 C 的一个负 sentinel 之外又加入第二个负对象，却没有先证明第二对象在同条件下
  可稳定命中；结果变化同时受对象内容、长度、数量和合并影响：
  同文件 `:355`、`:359`、`:375-376`。
- 架构固定“最小调用数 16 次”，但又允许 O 因没有第二个直接同标签原子对象而不合法，
  此时没有给出新的调用总数、答案路径集合和授权预算：同文件 `:361-376`。

**实际后果**

对照结果可能被误写为 brief、batch 或对象粒度的因果证据，继而选择错误的复考配置；
同时无法在派发前精确展开调用白名单、16 个答案路径和预算。该设计可以产生观察，不能
按当前判读规则稳定区分四个技术因素。

**最小修正方向**

架构修订须为每一臂列出逐字节输入、唯一变化量、组成对象的独立控制证据、合法性前置
和可支持的最窄结论。先冻结实际合法的臂集合，再计算并授权精确调用数、路径、预算与
停止条件；不满足单变量条件的臂必须降级为观察或移出因果结论。

### F-05｜P2｜产品材料与原子判词请求尚未精确到可交付问题

**证据**

- 架构先要求技术准备侧完成全候选 census 和原子准入：
  `diagnostics/T2.2-recovery-architecture-v1.md:251-275`。
- R0 却只泛称产品负责人须补足 3 个 positive 原文锚点，并让 14 个来源组都获得精确
  原子 scope：同文件 `:523-535`。
- blocker 仍只按“3 个 positive”“多陪读／整页样张”描述，没有列出精确来源、候选
  单元、缺失 scope 或待判问题：同文件 `:672-677`。

**实际后果**

目前无法生成一份最小、逐对象、可回答的产品请求；产品负责人可能被要求先做候选切分
和技术 census，或被过度请求整组材料／判词。下一张自包含任务卡也无法列出精确输入。

**最小修正方向**

先由技术角色在获准边界内形成逐来源、逐候选、逐 scope 的缺口清单，再只向产品负责人
请求清单中缺失的具体材料授权或具体原子判词。产品负责人决定材料与判词，不承担对象
切分、hash、选择算法或任务设计。

## 5. 已验证事实、推测与 unknown

### 5.1 已验证事实

- 起始 HEAD、工作区基线、被审 commit、架构文件 hash 和 commit 单文件范围均匹配。
- v1 八个关键文件的 SHA-256 与架构及 README 记录一致。
- 现行验证器把四张建议任务卡全部算作 unexpected。
- 路线图两处直接绑定无版本后缀的 v1 baseline。
- 架构文本没有覆盖、重命名或把 v1 `FAIL` 当作通过证据。
- 架构文本保持 T1.8、T2.1、T2.3、诊断端、裁判端和生产端的读取隔离。

### 5.2 技术推断

- 若直接创建建议任务卡，种子验证必然失败。
- 若不先修正 M2 接线，即使 v2 `PASS` 也无法按现行路线创建合法 M2 receipt。
- 当前冻结顺序不能唯一证明审查输入、brief 绑定和调用输入是同一最终字节。
- 当前对照最多支持局部观察，不能按架构现有语言唯一归因于 brief、batch 或对象合并。

这些推断都来自已读取的现行规则和架构内部关系，不依赖未授权材料或其他会话。

### 5.3 unknown

- 尚未创建的 adapter、admission、v2 packet、brief 和 taskcard 的实际正文与 hash。
- 哪些具体 positive 来源材料可获授权、其精确 scope 和原文锚点。
- 哪些多对象样张已经具有可直接适用于原子候选的产品判词。
- O 臂是否存在合法的第二个直接同标签原子对象。

- 任何未来对照、复考、M2、生产 semantic／product 结果或产品 `accepted`。

## 6. 产品决定

### 6.1 本次架构审查是否需要产品决定

不需要。现有 owner 文件足以证明架构存在技术与流程死路；产品负责人无需为了让本报告
得出结论而补材料、补判词或批准模型调用。因此不存在当前产品 blocker。

### 6.2 后续何时才需要产品决定

只有架构修订完成、技术角色产出精确 census 与缺口清单后，才向产品负责人提出以下
最小问题：

1. 是否授权清单逐项列出的 3 个 positive 对应原文摘录及其固定 scope 在新项目内用于
   v2 资格夹具？
2. 对清单逐项列出的、现有判词不能直接覆盖的原子候选，产品负责人是否确认既有判词
   适用、给出该原子对象的直接判词，或批准改变固定考试对象？

当前架构没有列出这些问题所需的精确对象清单，因此现在不得提前请求产品决定。
模型、reasoning、调用粒度、次数和预算还需要未来明确授权，但本次审查不请求授权。
