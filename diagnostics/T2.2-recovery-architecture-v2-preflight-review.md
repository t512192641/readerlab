## 6. 发现

### P0 — R03→R05 缺少完整 SOURCE-CONTEXT 字节交接

**位置**

- `diagnostics/T2.2-recovery-architecture-v2.md:388`
- `diagnostics/T2.2-recovery-architecture-v2.md:438`
- `diagnostics/T2.2-recovery-architecture-v2.md:472`
- `diagnostics/T2.2-recovery-architecture-v2.md:591`

**事实**

- R05 必须把 14 条候选和完整 SOURCE-CONTEXT 的最终字节写入 package。
- R05 明确不能读取 GOLD 或样张，只能读取冻结后的 R03 census、R04 review、产品输入和 material slots。
- R03 的 mandatory candidate schema 明确列出 candidate byte range/hash、标题、正文、caveat 完整性，以及 context identity/scope/range/hash/extraction rule；它没有明确要求 census 冻结并携带“将由 R05 逐字复制的完整 SOURCE-CONTEXT raw bytes”。

**为什么是执行死路**

hash 和 range 可以验证字节，却不能从自身恢复字节。若 R05 为取得缺失 bytes 重读样张，就违反自己的读取白名单；若把“context”解释为可由实施者自行重建，就违反最终 package 的 byte-stable、可复现要求。该缺口发生在任何模型调用之前，不能留给执行期猜测。

**最小修复方向**

在 v3 中把 R03 census 的强制 schema 改成：每个选中条目必须冻结候选最终 raw bytes 与完整 SOURCE-CONTEXT raw bytes、明确边界、对应 source range/hash 和提取规则；R04 对这些冻结 bytes 做独立 review；R05 只能逐字复制。另一种可行但边界更宽的方案，是为 R05 增加逐文件、逐范围的精确源读取许可。推荐前者，因为它保留了单向、可审核的数据流。

### P0 — R06 的“实际 material slots”无法在 21 卡原子注册时静态编译

**位置**

- `diagnostics/T2.2-recovery-architecture-v2.md:213`
- `diagnostics/T2.2-recovery-architecture-v2.md:236`
- `diagnostics/T2.2-recovery-architecture-v2.md:365`
- `diagnostics/T2.2-recovery-architecture-v2.md:386`
- `diagnostics/T2.2-recovery-architecture-v2.md:536`

**事实**

- C0 后必须先原子注册全部 21 张正式任务卡，验证器只允许 0 张或 21 张。
- R06 卡必须只列 R05 产生的“实际 material slots”。
- 实际缺口和 slot subset 只有完成 R03 census、R04 review 和 R05 请求编译后才知道。
- 架构同时禁止 dynamic branch、optional file、glob 和 runtime-expanded path。

**为什么是执行死路**

A3 时没有足够信息写出 R06 的精确静态 whitelist。预列 14 个 slots 会超出“实际 slots”；猜 subset 不可验证；事后改卡会破坏先注册、后执行和冻结卡的原子前提；使用动态路径又被明令禁止。

**最小修复方向**

在 v3 中固定一种无歧义机制。推荐把 R06 静态白名单定义为 14 个精确、预命名 slot paths，并增加硬规则：只有 R05 冻结 gap manifest 中列出且真实存在的 slots 可被打开，其余路径不得探测；同时把这种“固定封闭候选集合 + 冻结 manifest 选择”明确列为允许机制，而不是 optional/dynamic path。若不采用此机制，就必须合法化一个 R05 后的二阶段卡编译点，并重写 0/21 原子注册合同。

### P1 — 未来 stateful artifacts 缺少逐路径 scope 决议

**位置**
