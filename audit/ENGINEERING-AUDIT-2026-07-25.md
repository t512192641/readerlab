## 2. 结论

当前生产流程作为“研究和定位问题的实验流程”基本合理，但还不是成熟的最终生产系统。它已经能够把失败定位到发现、选题、Expert、来源、Writer 或装配等不同阶段；真正的问题是实验规则、最终 Skill 架构和当前状态记录混在一起，造成规则持续增长、状态互相冲突、测试长期为红、一次性任务卡越来越像手工程序。

当前最小正确路线不是继续自动化，也不是再增加一道门。应先完成 T2.35 产品审阅，修复会污染验证信号的工程问题，再让 D3 走完 Writer → Fidelity → 装配 → P3。只有新配置第一次获得产品接受，才有资格冻结最小生产合同并进入后台编排和 Skill 化。

## 3. 当前真正到达的位置

| 层级 | 当前事实 |
|---|---|
| `implemented` | T2.35 的 D3 Expert、5 张知识卡、来源审核、P2 gate 和审阅包存在 |
| `integrated` | 当前任务只集成到来源审核／P2，没有进入 Writer、Fidelity、装配或 P3 |
| `verified` | 冻结清单内文件哈希一致；但当前 `tools/run.py check` 因 `.DS_Store` 失败，现场已不能继续声称完整 PASS |
| `accepted` | 产品负责人尚未对 T2.35 Expert 作是否值得进入 Writer 的判词；Reader 和 P3 均不存在 |

因此，T2.35 不能被称为“新配置的首次完整端到端验证”。它只验证到 P2。

## 4. 生产管线是否合理

### 合理的部分

1. **责任拆分正确**：发现、比较、Expert、来源审核、Writer、Fidelity 和产品判断承担不同责任，避免 Writer 救上游选题、审核者重写课程或技术检查替代产品判词。
2. **冻结与排他 promotion 有价值**：现有 `tools/run.py` 用较小 interface 覆盖候选哈希绑定、外部 validator、排他发布、`fsync`、freeze 和 check，是有 depth 的 module，不应因文件较长就机械拆碎。
3. **低成本否决方向正确**：T2.34 在完整展开前做四向比较，避免继续沿用 T2.33 的过宽候选，属于正确的成本前移。
4. **工具路线已经纠偏**：来源研究默认使用 Web Search／Web Fetch，并禁止 Chrome remote debugging 和浏览器自动化；T2.35 未再出现 T2.33 的 46 分钟 Chrome 阻塞。
5. **技术与产品分层清楚**：T2.28、T2.30、T2.31、T2.33 都保留了“技术链通过但产品未接受”的真实记录，没有篡改历史结果。

### 尚不合理的部分

1. **新配置从未端到端获得产品接受**：T2.28、T2.30、T2.31、T2.33 共四次 P3 均未接受；T2.35 尚未进入 P3。
2. **失败后规则增长过快**：C4 收紧、Writer 前置指令、自检、四向比较、范围门等连续加入，但没有一份接受稿证明这些规则组合后仍能走通。
3. **研究流程被误当成最终架构**：当前仍需要大量任务卡、人工派发、路径搬运和一级会话；这些在研究期可接受，不能直接成为用户使用的 Skill。
4. **一次性任务卡承担了过多实现**：仓库有 65 张任务卡、共 11,771 行；仅 T2.28—T2.35 八张卡已有 1,810 行。通用验证和状态逻辑反复写进任务卡，locality 很差。
5. **状态事实散落且互相冲突**：README 仍停在 T2.12，派生路线说明停在 T2.25／T2.26，蓝图的当前停点更早，旧审计宪章则写 T2.35 待跑。陌生 Agent 无法从一个可信 interface 得到当前状态。

## 5. 主要审计发现

### A. 当前状态入口失真

严重程度：高。

`README.md` 自称“唯一交接入口”，但内容仍把 T2.12 写成当前下一步；`docs/book-pipeline-current-state-and-skill-roadmap.md` 仍把第三个未动章节 T2.26 写成下一步；实际现场已到 T2.35。多个文档拥有同一状态正文，违反单一事实 owner 原则。

影响：

- 新执行者可能选择错误入口；
- 审计结论和生产计划会基于过期事实；
- 每次运行都要人工更新多个位置，必然继续漂移。

建议：

- 立即先指定并修正一个当前状态 owner，其他文档只引用，不再复制正文；
- 如果后续仍发生状态漂移，再建立只读 Run Status Projection module，从 taskcard 绑定、run metadata、freeze、acceptance 和产品判词生成当前状态；
- 在必要性得到证明前，不先建设新的状态系统。

### B. T2.35 与原审计计划不一致

严重程度：高。

原宪章要求 T2.35 完整走到 P3，并在 Expert 后执行范围门；实际任务卡明确停在 P2，禁止 Writer、Fidelity、装配和 P3。T2.35 Expert 为 27,640 bytes，超过原范围门的 20,000 bytes 上限，但范围门没有执行。

这不是自动等于 T2.35 内容失败。它证明的是：

- 原宪章对 T2.35 的状态陈述已经过期；
- 20,000 bytes 不能被静默当作现行硬门；
- Writer 前仍需要判断这堂课是否能在一篇 Reader 中被普通读者掌握。

建议把“范围门”分成两层：

- **语义硬门**：每条候选 Reader 的主要认识是否连贯，多张相连知识卡是否共同承重，完整章节的 0—N 条陪读是否造成不可接受的阅读负担；
- **机械警报**：bytes、概念数和案例数只触发检查，不直接代替产品与教学判断。

### C. 当前 run 的健康检查会被宿主元数据破坏

严重程度：阻塞下一轮正式生产前的技术收口。

实际执行：

```text
python3 -B tools/run.py check runs/T2.35-CH08-D3-EXPERT-P2-01
```

当前结果：

```text
run error: unexpected path at run root: .DS_Store
```

`.gitignore` 已明确忽略 `.DS_Store`，但 `tools/run.py` 对 run 根目录所有未知路径硬失败。T2.28 Writer、T2.30、T2.31、T2.35 四个 run 都出现同类问题。打开 Finder 就可能让原本通过的冻结 run 变红。

建议：

- 建立 Artifact Inventory 内部 module；
- freeze 和 check 使用同一个 inventory 实现；
- 对明确列出的宿主元数据受控忽略并发出 warning；
- 其他未知文件继续硬失败；
- 增加回归测试，避免人工逐 run 删除。

### D. 默认测试信号长期失真

严重程度：高。

全仓测试实际为 35 项中 24 PASS、1 FAIL、10 ERROR。11 项失败都属于历史 T2.26：

- 7 项绑定旧 Writer v1.3 字节数；
- 4 项绑定旧任务卡或 Git identity。

这些测试并未告诉我们“当前生产管线坏了”，却让默认全仓测试长期保持红灯。团队因此会逐渐忽略测试结果，真正的新失败也更难被发现。

仓库级 `python3 -B validate.py` 也未通过：当前 taskcard 集合超出验证器冻结清单，多个后续任务卡触发旧引用规则，内部 manifest 与当前仓库不一致。这是同一类问题——默认项目健康入口已经落后于实际开发现场。

建议建立两个真实 adapter：

1. `active`：当前生产和共享工具的默认测试，必须全绿；
2. `historical T2.26 replay`：显式运行，报告冻结身份是否仍可复算，不污染默认健康信号。

### E. 通用工程能力仍散落在一次性任务里

严重程度：中高。

T2.30 曾为一次 run 创建 10 个临时脚本；后续任务改用一次性 inline validator。通用的 UTF-8、字段、lineage、父 SHA、锚点、装配和 acceptance 绑定没有全部集中在稳定 module 中。`tools/run.py` 当前只拥有 run 根身份、promotion 和终局 freeze，不绑定 taskcard SHA、阶段 checkpoint、终局状态或 artifact profile。

建议深化现有 run module，不重写：

- 参数化 artifact profile；
- taskcard／experiment binding；
- 阶段 checkpoint receipt；
- 通用验证集中实现；
- 样本特有语义继续留在任务卡。

这样能获得 leverage 和 locality：一处修复，所有 run 受益；测试只需跨一个 interface。

### F. 当前存在明显的过拟合风险

严重程度：高。

证据链：

- T2.28 因外部知识不承重被拒，随后收紧 C4；
- T2.30／T2.31 因 Writer 组织问题补丁化；
- T2.32 新指令下没有候选通过 C4；
- T2.33 有真实知识但范围和教学组织失败；
- T2.34 又增加四向比较；
- T2.35 改为单方向 Expert 与 P2。

每一步都有局部理由，但组合后尚未产出新接受稿。继续为 D3 增加新的长期 Prompt 或硬门，会进一步提高对第 8 章的过拟合风险。

建议：

- 在 T2.35 产品判断前不新增长期规则；
- 下一次端到端运行中冻结现有合同；
- P3 若失败，只定位失败发生在哪个责任，不无差别加门；
- P3 若接受，再从跨样本稳定部分提炼共享合同。

## 6. 北极星指标

后续每次正式审计建议固定观察：

| 指标 | 小白解释 |
|---|---|
| 第一版产品接受率 | 不靠多轮救稿，第一次交付有多少真正可用 |
| 冻结流程复现率 | 不改规则，换材料还能不能成功 |
| 活跃测试通过率 | 当前真正使用的工程能力是否全绿 |
| 重复事故数 | 同类 bug 是否再次收费 |
| 工具无效时间 | Chrome 死锁、超时、编码失败浪费多少分钟 |
| 端到端关键路径 | 不含产品等待，系统最快需要多久完成 |
| 每个接受结果的调用与返工 | 为得到一个可用产物花了多少模型和修订 |
| 一次性资产增长 | 是否又为单次 run 增加脚本、字段和特殊规则 |
| 用户可见操作数 | 最终用户需要亲自管理多少内部步骤 |

指标不是新的产品门。它们帮助发现路线是否越来越慢、越来越贵、越来越复杂。

## 7. 从现在到图书 Skill 的整体计划

下面是六个阶段，不等于固定六张任务卡；每阶段只有达到停止条件才进入下一阶段。

### 阶段 1：T2.35 产品审阅与工程收口

产品负责人只判断：

> D3 这堂完整 Expert 课是否值得进入 Writer，以及是否能被收成一篇普通读者可掌握的 Reader。

执行现场同时修复：

- `.DS_Store` 造成的 run check 失真；
- 默认 active 测试与历史回放测试混杂；
- T2.35 工作树和完成报告的技术收口。

停止条件：

- 产品判 `STOP`：D3 不进入 Writer；
- 产品判 `WORTH_WRITING`：进入阶段 2；
- 当前 run 未恢复可验证状态：不得启动下一轮生产。

### 阶段 2：D3 完成首次新配置端到端

另开明确任务，只做：

```text
已接受 Expert
  → 必要范围收窄
  → Writer
  → Fidelity
  → 确定性装配
  → P3
```

运行中不修改长期 Prompt、不增加新门、不换材料补考。

停止条件：

- P3 接受：证明新配置至少成功一次，进入阶段 3；
- P3 拒绝：按产品判词定位责任，停止叠加规则，先做根因审计。

### 阶段 3：冻结流程在未见材料上复现

选择新的完整章节，在运行前冻结全部合同和工具，不为样本修改规则。目标不是再得到一篇“最后修好的稿”，而是证明同一流程可以复现。

至少验证：

- 第一版质量；
- 是否出现合法零陪读；
- 是否需要语义返工；
- 工具和等待时间；
- 候选、Expert、Writer 与 P3 的失败位置。

### 阶段 4：目标档模型与成本验证

用日常计划使用的中等偏上模型，在另一份未见材料上运行冻结流程。最强模型只用于离线诊断，不成为每章必经步骤。

成功条件：

- 产品质量达到目标；
- 活跃测试全绿；
- 无重复工程事故；
- 墙钟、调用和返工在可接受范围；
- 不依赖人工修改 Prompt 救场。

### 阶段 5：后台编排与图书 Skill v0.1

此时才把已经验证的责任迁入一个用户可见入口：

- 材料进入和范围冻结；
- 后台角色调度；
- artifact、checkpoint 和状态；
- 重试与停止；
- 时间和 usage；
- 单一进度与审阅包。

角色隔离继续保留，但不要求产品负责人手工管理多个一级会话。

### 阶段 6：影子回归与小规模上岗

- 用已接受样本做回归；
- 用新章节比较人工流程和 Skill 流程；
- 检查内容、来源、Writer、锚点、装配、速度和成本是否等价；
- 产品负责人接受后再小规模扩产；
- 随运行数据治理正式透镜、版本和退役。

## 8. Skills 产品线的后续计划

Skills 线与图书线共享的只应是薄工程骨架：

- 材料身份和 scope；
- 哈希、冻结和 receipts；
- 读取隔离；
- 状态、时间、usage 和错误恢复；
- 单一用户入口。

不能共享图书线的 B2 产品标准、Expert／Writer 语义合同、Judge 或通过证据。

建议四个阶段：

1. 选择一个获授权 Skills 包，人工完成 E1—E4 端到端样张；
2. 用第二个不同 Skills 包验证冻结合同和合法归零；
3. 把已验证流程接入共享编排骨架；
4. 形成 Skills 解读 Skill v0.1，并做人工流程对照。

当前仓库仍没有可称为已运行并获得产品接受的 Skills runtime、Demo 或产品样张，因此不能把图书线进展直接算作 Skills 线进展。

## 9. 推荐的当前下一步

按顺序：

1. 产品负责人阅读 T2.35 审阅包，只决定 D3 是否值得进入 Writer；
2. 执行现场在下一次生产前修复 run check 和 active 测试信号；
3. 若 D3 通过，另开 Writer → Fidelity → 装配 → P3；
4. 审计官复核承诺、实际行动、时间、调用和 P3 结果；
5. P3 接受后才讨论后台编排和 Skill 化；拒绝则先根因审计。

当前不建议：

- 立即自动化全流程；
- 再增加长期 Prompt 或硬门；
- 把 20,000 bytes／1,800 字直接固化为产品上限；
- 恢复 Judge；
- 启动 B3；
- 扩大到多 callout；
- 用更多一次性脚本修当前样本。
