# ReaderLab 审计运行机制

> 版本：v0.1
> 状态：试运行
> 最后更新：2026-07-25
> owner：工程审计体系
> 用途：定义何时审、由谁审、读什么、交付什么，以及审计结论怎样约束下一步。

## 一、目标与非目标

本机制把工程审计做成一个小 interface：

```text
固定目标与获批范围
  + 实际变更、run、测试、成本和产品判词
  + 相关开放问题
        ↓
独立审阅与证据核对
        ↓
GREEN / YELLOW / RED
  + 证据边界
  + 下一允许动作
  + 修复责任与复核条件
```

执行现场不需要学习审计内部怎样分工，只需提交本轮真实证据。审计体系内部可以按需使用多个独立审阅者，但最终只向产品负责人暴露一份合并结论和少量必要决定。

本机制不负责：

- 定义或改写产品目标；
- 生产 Expert、Reader、E1—E4 或产品判词；
- 编写生产任务卡或修复生产实现；
- 用审计票数代替直接证据；
- 用更多字段和报告代替真实运行；
- 把试运行频率冻结为长期产品规则。

## 二、三个常驻责任方

### 产品负责人

- 提供产品目标、优先级和真实产品判词；
- 决定重大产品方向、公开行为和长期责任变化；
- 不承担技术实现、文件结构、测试、角色调度或故障恢复设计。

### 执行现场

- 提出技术方案并在获批范围内实施；
- 保存实际变更、运行、成本、偏差和验证证据；
- 处理审计发现并提交可复核结果；
- 不自行关闭需要独立复核的问题。

### 审计总控

- 选择适用审计类型；
- 冻结本轮固定点和最小证据包；
- 临时启用必要审阅责任；
- 独立抽查直接证据，汇总结论；
- 更新能力地图和问题台账；
- 不接管生产实现或产品判断。

## 三、四种临时审阅责任

它们是按需启用的责任，不自动等于四个永久 Agent。

### 变更一致性审阅

回答：承诺、授权、实际修改和完成结论是否一致？

最低检查：

- 获批目标、范围、文件和停止点；
- 实际 Git diff、运行路径和外部动作；
- 是否存在夹带修改、死代码、占位或越级完成；
- implemented、integrated、verified、accepted 是否被混用。

### 可靠性与证据审阅

回答：结果是否可复验，同类事故是否会再次收费？

最低检查：

- 真实入口、测试、构建、run check 和冻结证据；
- 重试、覆盖、污染、超时和工具故障；
- Agent 自报与文件系统、Git、日志是否一致；
- 默认健康信号是否仍可信。

### 架构与路线审阅

回答：当前行动是否仍通往包含两条独立产品线的成熟 Skills 交付，完整责任是否缺失或错位？

最低检查：

- 从最终交付反推的功能责任；
- 研究期关卡与最终生产责任是否混淆；
- 路线是否对同一材料、模型或局部指标过拟合；
- 两条产品线是否错误共用语义标准；
- 当前里程碑和停止条件是否真实。

### 简洁性与成本审阅

回答：新增复杂度、角色、等待和调用是否产生了相称收益？

最低检查：

- 角色和关卡删除测试；
- 一次性任务卡、脚本、字段和人工搬运；
- 模型时间、真实墙钟、工具等待、重试和返工；
- 修一个问题是否需要修改大量位置；
- 最终用户是否被迫管理内部复杂度。

## 四、五种审计

### 1. 变更检查

触发：

- 一次重要实现、修复、合同调整或生产 run 结束；
- 执行现场申请进入下一阶段；
- 产品负责人或审计总控要求核对范围。

默认范围：只读本轮获批目标、相关 diff、直接调用点、测试、run 和关联开放问题。

输出：`GREEN`、`YELLOW` 或 `RED`，以及下一允许动作。

### 2. 小审计

试运行频率：人工打磨阶段每两轮有实质产出的迭代一次。以下事件可提前触发：

- 同类失败第二次出现；
- 规则、角色或必填字段继续增长；
- 产品结果与技术结果连续背离；
- 当前路线或状态说明出现新的冲突。

范围：最近两轮及其共同依赖，不默认重读全部历史。

目标：发现局部偏航、重复事故、过拟合和成本异常。

### 3. 大审计

试运行频率：每五轮有实质产出的迭代或每个关键里程碑一次，以先到者为准。以下事件立即触发：

- 连续两次产品失败；
- 准备增加长期角色、关卡或公共合同；
- 准备宣布某项能力取得资格；
- 准备进入自动化、Skill 化或发布；
- 已无法从唯一入口确定当前状态；
- 产品负责人要求从终局重新校准路线。

范围：产品北极星、完整能力地图、相关架构、当前实现、历史产品证据、工程健康和成本。生产／金标读取隔离继续有效。

目标：判断整条路线是否仍合理、完整和经济。

### 4. 工程事故审计

立即触发：

- 无价值阻塞超过十分钟；
- 同类 bug 或工具事故第二次发生；
- 正式产物被覆盖、污染或无法复验；
- 默认测试或状态入口给出误导信号；
- 实际行为与执行报告不一致；
- 证据、权限或冻结边界可能受损。

事故审计必须同时回答：

1. 直接影响是什么；
2. 为什么现有防线没有阻止；
3. 同类操作还出现在哪些阶段；
4. 恢复是否改变历史证据；
5. 怎样通过真实回归证明不再复发。

### 5. 资格／发布审计

适用于正式透镜、Expert、Writer、Judge、图书 Skill、Skills 解读 Skill 或其他被宣称可复用的能力。

最低前置：

- 合同和实现冻结；
- 未见材料；
- 目标档运行条件；
- 生产与验收隔离；
- 已接受正例和明确反例的适用回归；
- 可复算的时间、调用、错误与产品判词；
- 不依赖同一样本临时改 Prompt 或加门救场。

一次成功只能证明一次成功，不能自动得到资格。

## 五、冷启动入口与最小证据包

### 5.1 全新上下文冷启动

全新审计者必须先遵守项目 `AGENTS.md`，不存在由本机制私自建立的读取豁免。只为恢复项目目标和当前审计状态时，按顺序读取：

1. `AGENTS.md`；
2. `PRODUCT-DECISIONS.md`；
3. `ENGINEERING-LESSONS.md`；
4. `blueprints/PIPELINE-MAP.md`；
5. `audit/CAPABILITY-MAP.md`；
6. `audit/FINDINGS-REGISTER.md` 顶部的唯一当前行动门和相关问题。

只有要实际组织或执行正式审计时，再读取本运行机制和 `audit/ENGINEERING-AUDITOR-CHARTER.md`。最近报告、任务卡、run 和代码不是冷启动默认全文；它们按本轮证据坐标展开。

### 5.2 单次审计证据包

每次审计由审计总控逐项冻结，在上述项目强制入口之外默认只增加：

1. 本轮获批任务、固定点和明确停止条件；
2. `audit/FINDINGS-REGISTER.md` 中相关开放问题；
3. 实际 diff、run、测试、墙钟、调用和产品判词；
4. 为核对直接证据所必需的最小代码、合同或历史坐标。

审阅者不得因为“可能有帮助”就默认读取全部任务卡、全部 run、金标、样张或历史总结。发现证据缺口时先报告缺什么和为什么需要，再由审计总控判断是否扩展。

## 六、审计结果

### GREEN

直接证据支持本轮结论，没有阻塞下一允许动作的问题。

### YELLOW

可以在明确条件下继续。报告必须写清：

- 哪些问题尚未关闭；
- 允许继续到哪里；
- 哪些动作被禁止；
- 最晚何时复核。

### RED

必须停止当前推进。适用于：

- 无法确定真实状态；
- 路线、授权或事实 owner 冲突；
- 技术 PASS 被冒充为产品接受；
- 同一错误假设机械重跑；
- 正式证据可能受损；
- 新增复杂度没有可说明的责任或收益；
- 资格结论缺少未见材料或独立验证。

RED 不授权审计总控直接修复。

## 七、问题状态与关闭

问题状态只有：

- `OPEN`：已确认，尚未处理；
- `IN_PROGRESS`：执行现场正在处理；
- `READY_FOR_REAUDIT`：执行现场自报处理完成，等待独立复核；
- `CLOSED`：审计依据直接证据确认关闭；
- `SUPERSEDED`：问题描述被更准确的问题取代，旧记录仍保留。

每个问题必须有：

- 唯一 ID；
- 事实与证据；
- 影响；
- 处理责任；
- 是否阻塞；
- 允许动作；
- 复核条件。

不能用“已整理”“应该没问题”或执行者自报关闭。

## 八、角色和关卡删除测试

任何长期角色、关卡、字段或独立调用都要回答：

1. 防止哪种已经发生或有充分依据的失败？
2. 判断对象是否与现有责任不同？
3. 是否需要独立信息权限或独立判断权？
4. 失败后是否触发与其他角色不同的动作？
5. 能否合并到现有责任而不损失隔离、可靠性或可诊断性？
6. 删除后，复杂度是消失还是转移到多个位置？
7. 时间、调用、上下文和维护成本是否得到产品收益偿还？

回答不清时，默认不进入长期流程。研发期临时关卡必须注明失效条件。

## 九、报告最小格式

每份正式报告按顺序包含：

1. 本轮创建或修改过的全部 run 和文件；
2. 固定点、范围和未读内容；
3. `GREEN`／`YELLOW`／`RED` 结论；
4. 承诺与实际行动；
5. 证据只证明到哪一层；
6. 问题、影响和严重程度；
7. 重复事故、浪费和过拟合；
8. 对最终 Skills 交付中两条产品线的影响；
9. 下一允许动作、禁止动作和复核条件；
10. 需要产品负责人决定的最小问题。

## 十、试运行复盘

“每两轮小审计、每五轮大审计”只适用于当前人工打磨期。完成两次小审计和一次大审计后，必须复盘：

- 审计发现的问题是否足以偿还成本；
- 是否存在重复审阅；
- 最小证据包是否仍过大；
- 哪些临时责任需要合并；
- 是否可以降低频率；
- 是否有任何审计字段已经变成无价值填写。

未经复盘，不把试运行参数提升为长期规则。
