## 这是正文：净化后的主流程

`browse` 要解决的问题很具体：Agent 不能只靠猜测判断网页有没有跑通，它需要一个能真正打开页面、点击、填表、看控制台、看网络请求、截图、比较前后状态的浏览器工具。

它的默认形态是一个持久的 headless Chromium。第一次调用会启动浏览器，后续命令复用同一个浏览器状态；cookie、标签页、登录态和页面历史不会每次都丢失。对用户来说，这意味着 Agent 可以像一个持续操作同一台浏览器的人，而不是每一步都从零打开新窗口。

核心使用路径分成几类：

1. 导航与读取：打开 URL，读取页面文本、链接、表单、结构化数据、可访问性树、控制台日志和网络请求。
2. 交互与断言：点击、填写、选择、滚动、等待元素、检查按钮是否可见 / 可点 / 已选中。
3. 视觉证据：截图、带标注截图、响应式截图、PDF、两个页面的差异对比。
4. 本地渲染：把本地 HTML 或内存生成的 HTML 放进浏览器，输出截图或文件。
5. 复杂站点处理：遇到验证码、多因素登录或强反爬时，把浏览器交给用户接管，用户处理完后再恢复 Agent 控制。

这套能力没有直接暴露成“随便执行浏览器内部任何东西”。它把命令分成读、写、管理、可视化、标签页、服务端等类型；有些命令只是读取页面，有些会改变页面状态，有些能写文件，有些能影响整个浏览器。

对网页内容的读取也默认带防线。页面文字、HTML、链接、表单、控制台、弹窗和截图树都可能包含第三方网页写给 Agent 的恶意指令，所以 `browse` 会把这些输出包进“不可信网页内容”的边界里，并且对隐藏元素、ARIA 注入、可疑 URL 做额外处理。

当多个 Agent 或远程 Agent 共用浏览器能力时，`browse` 不把主权限直接发出去。它用 root token 派发带范围的子 token：有的只能读，有的可以写，有的才有高级权限；还可以限制域名、限制速率、限制只能操作自己的标签页。

文件读写同样有限制。截图、PDF、下载、归档、脚本输出这类写文件动作只能写到允许目录；远程取文件时只允许取临时目录里的文件，不能让远程 Agent 顺手读项目文件。

Chrome DevTools Protocol 也没有全开放。它只允许一个白名单里的方法；页面导航、任意网络读取、容易泄露内容的方法默认不开放。也就是说，`browse` 提供了必要的浏览器底层能力，但没有把整套浏览器调试接口裸露给 Agent。

## 这是产品解读：它到底帮用户解决什么

`browse` 的产品价值不是“有一个浏览器命令行”。它真正解决的是 AI 做网页验收时最常见的三个断层。

第一个断层是证据断层。很多 Agent 会说“看起来应该可以”，但没有真的打开页面、没有点按钮、没有截图、没有看控制台错误。`browse` 把判断变成可观察动作：打开、点、查、截图、比对。

第二个断层是状态断层。网页 QA 往往不是单步动作，而是一串带状态的流程：登录后再进入 dashboard，点弹窗后再确认状态，切移动端再截图。如果每个命令都启动新浏览器，流程就断了。`browse` 用持久浏览器保留状态，让 Agent 能做连续验证。

第三个断层是安全断层。网页是外部输入，页面内容可能诱导 Agent 执行不该执行的事；浏览器本身又可能接触 cookie、文件、下载和本地路径。`browse` 的大量“重设计”都在防这个：网页内容不可信、权限分层、文件路径限制、CDP 白名单、远程 Agent 隔离。

所以它不是一个轻量截图器，而是一个“给 Agent 用的浏览器操作平台”。它把浏览器变成可复用的证据采集器，同时承认浏览器是危险边界，不能只追求方便。

## 这是技术解读：为什么它设计得这么重

从产品负责人视角看，`browse` 最反直觉的地方是：明明只是打开网页，为什么要有服务端、token、标签页所有权、路径校验、CDP 白名单、内容安全层和用户接管？

原因是浏览器不是普通工具。浏览器同时接触三类高风险东西：外部网页内容、用户登录态、本机文件系统。任何一个边界松了，Agent 看到的网页文字就可能变成指令，或者远程 Agent 拿到过大权限，或者截图 / 下载命令被绕成文件读写通道。

第一层设计是“持久守护进程”。浏览器由本地服务端统一管理，CLI 命令只是把动作发给这个服务端。这样做的代价是系统复杂很多：要管端口、空闲超时、浏览器崩溃、状态文件、父进程退出。但收益是状态连续、启动更快、多个命令共享同一浏览器，不用每次重新建上下文。

第二层设计是“命令注册表”。`commands.ts` 把命令分成读取、写入和元命令，并且同一份定义给运行时、文档生成、校验和健康检查复用。这个设计防的是“文档说有、运行时没有”或“新增命令忘记进权限模型”。对非工程读者来说，它像一本总账：所有按钮都先登记，再决定谁能按。

第三层设计是“权限不是一把钥匙”。`token-registry.ts` 把权限拆成读、写、管理、元操作、控制浏览器等范围。危险点在于：`js`、`eval`、cookie、storage 看起来像读取，实际能读敏感状态或执行页面脚本，所以被归入更高权限。这个判断比简单的读 / 写分类更成熟。

第四层设计是“网页内容默认不可信”。网页返回的文本、HTML、可访问性树、控制台内容都可能夹带给 Agent 的指令。`content-security.ts` 做了几件事：给文本加隐形标记，识别隐藏元素和 ARIA 注入，把页面内容包进不可信边界，给后续过滤器留接口。这不是为了洁癖，而是为了防网页把自己伪装成系统消息。

第五层设计是“文件路径有围栏”。`path-security.ts` 规定本地命令只能在临时目录或当前工作目录读写，远程文件服务只能取临时目录，还会解析符号链接，防止路径看似在安全目录、实际指向外部敏感文件。

第六层设计是“CDP 默认拒绝”。Chrome DevTools Protocol 很强，强到可以绕过正常网页命令。`cdp-allowlist.ts` 只开放少量方法，并给每个方法标注作用域、输出是否可信和允许理由。这里的取舍很清楚：宁可多写白名单，也不把底层浏览器调试能力直接交给 Agent。

第七层设计是“用户接管不是失败，而是流程的一部分”。验证码、OAuth、多因素登录、强反爬，本来就不适合让 headless Agent 硬闯。`handoff / resume` 把浏览器交给用户，用户处理完再恢复自动化。这个设计承认自动化边界，避免把登录和反爬问题伪装成可自动解决。

第八层设计是“大量测试在保护产品风险图谱”。`browse` 的测试不是只测函数输出，而是在测安全、权限、服务端、侧边栏、终端会话、cookie、代理、截图、文件投放、CDP、内存和 tab 隔离。它像是在问：如果把浏览器借给 Agent，哪些方向最可能出事故？

## 结构地图

`gstack/browse` 可以切成六个功能块：

1. 使用者入口：`SKILL.md` 告诉 Agent 什么时候用、怎么用、遇到登录 / 验证码如何交接。
2. 命令层：`commands.ts`、`read-commands.ts`、`write-commands.ts` 和 `meta-commands.ts` 定义浏览器可做的动作。
3. 浏览器状态层：`browser-manager.ts` 管 Chromium、context、tab、viewport、cookie、handoff 和崩溃恢复。
4. 服务与权限层：`server.ts` 负责 HTTP 路由、token 验证、命令派发、隧道、SSE、终端会话和多 Agent 隔离。
5. 安全边界层：`token-registry.ts`、`path-security.ts`、`content-security.ts`、`security.ts`、`cdp-allowlist.ts` 负责权限、路径、网页内容、提示注入和底层调试接口。
6. 验证层：`test/` 里的大量测试覆盖这些边界是否真的起作用。

## 读完带走

- `gstack/browse` 的核心不是截图，而是“让 Agent 用浏览器拿证据，同时不把浏览器危险能力裸露出去”。
- 它最值得 ReaderLab 继承的是三件事：证据化交互、状态连续、危险边界分层。
- 它最不该照搬的是整段 gstack 通用启动壳。那些内容对真实 Skill 运行有意义，但在读者主正文里会污染理解；应放进技术解读或 audit。
- 这个样本比 `gstack/spec` 更能测试技术负责人页上限，因为它有真实代码结构、权限模型、安全模型和浏览器生命周期。
