## 逐卡结果

### 卡 1：五问锁 Why 门

- 问题：防止 Agent 把一句模糊愿望直接包装成看似完整、实际不可执行的 issue。
- 做法：先锁定五个基础问题：谁受影响、现在发生什么、应该怎样、为什么现在做、怎样算完成。
- 边界：适合用户已经想进入 backlog，但需求还缺少执行条件的场景；不适合纯探索、闲聊，或还没决定是否要做的想法。
- 第一步：先问五个问题；五问未闭合前，不进入方案设计。
- 演练：场景“把阅读包体验优化一下，先建个 issue。”启用此卡，因为这句话还不知道受影响对象、当前问题、目标行为、优先级原因和验收标准。
- 冷启动结论：基本自足。

### 卡 2：读证据后再问技术问题

- 问题：防止 Agent 用通用 checklist 问用户，让用户替 Agent 做项目定位。
- 做法：在问技术实现、数据、接口、测试、架构问题前，先读项目里的相关证据，再只问证据无法回答的问题。
- 边界：适合项目内功能、bug、重构、架构任务；绿地任务也要先说明搜索了什么、没有找到现有证据。
- 第一步：先搜索或阅读最可能相关的项目文件、目录或配置，并在后续问题中引用证据。
- 演练：场景“这个生成脚本为什么没有产出 manifest？”启用此卡，因为这是项目内 bug，Agent 应先看相关脚本、配置或输出，再问用户不能从证据判断的问题。
- 冷启动结论：可用，但不够完全自足。缺口是没有定义复杂项目里“读到什么证据才算够”，可能导致读得太少或问得太早。

### 卡 3：出口扫描与执行前保护现场

- 问题：防止 spec、issue、归档或交给新 Agent 的材料泄露敏感内容，或让新执行者基于脏 worktree 开工。
- 做法：凡是内容要离开当前对话，先审查精确文本并做脱敏扫描；如果要 spawn agent，还要检查 worktree 状态，并让用户选择继续、stash 或取消。
- 边界：适合发 GitHub issue、长期归档、交给另一个 Agent、公开或半公开出口；不适合只在当前对话里临时思考且不落盘的草稿。
- 第一步：先对即将送出的精确文本做语义审查和脱敏扫描；如涉及新 Agent，再检查当前 worktree 是否干净。
- 演练：场景“把这段 spec 发成 GitHub issue，然后让另一个 Agent 开工。”启用此卡，因为内容要进入外部系统并派生执行，必须先检查敏感信息和现场状态。
- 冷启动结论：可用，但不够完全自足。缺口是没有列出脱敏扫描的具体检查项，例如密钥、PII、人名负面判断、内部策略、未公开路径等。
