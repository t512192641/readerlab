## 一、从五份合同重建的任务顺序

1. `skill-source-integrator`：读取已登记原始材料，产出净化正文、source map、删除记录与关联资产清单。
2. `skill-mechanism-auditor`：只基于净化正文、source map、关联资产和获准事实证据生产完整机制候选；不写最终文案、不自评通过。
3. `skill-judge`：独立核对候选的来源、绝对价值和边界，逐项 `accept | reject | blocked`，允许 0 条，并锁定可交给成文者的机制包。
4. `skill-writer`：只把锁定机制包写成读者可见技术负责人页，同时原样装配净化正文；不改题、不补事实、不复活落选项。
5. `cold-start-reproducer`：先只看最终读者页做冷读，再只依赖 manifest 声明的最终资产做适用的冷启动或复现，最后收窄声明范围。

重建结论：五任务的数据流可由合同独立恢复为：

`登记源材料 → 净化正文/source map → 完整机制候选 → 独立裁判锁定包 → 主读页/技术负责人页 → 冷读与冷启动/复现证据`

没有发现裁判先于候选、成文先于锁定或冷读接触生产过程的倒序。

## 二、逐角色检查

## 1. skill-source-integrator

- 合同判定：`fail`（成功路径清楚；停止路径无法按 schema 表达）。
- 任务：清楚。唯一任务是从已登记源材料建立可追溯净化正文和 source map，没有混入机制解释或质量裁判。
- 允许输入：边界清楚，只允许主控提供的两条专属规则摘录、已登记源材料与范围声明。没有要求完整协议。
- 输出 schema：成功路径基本完整。`clean_units` 能记录可见文本、全部来源动作和实际处理；`deletions` 单列重要删除及去向；`related_assets` 防止模板、脚本、参考资料冒充主体；`gaps` 可留缺口。
- 禁令：能保护一手主体。明确禁止 AI 总结、方法命名、评价、建议和外部比较替代净化正文，也禁止改写机制与不可追溯推断。
- 停止条件：触发条件完整，覆盖未登记、关键源缺失、冲突改变机制和必须实质改写四类情形。
- 自足性：正常成功路径可仅凭本合同和允许运行输入执行；失败路径不自足。合同要求“停止并上报”，但 schema 没有整体 `status`、`blocked_reason`、冲突位置或退回对象。若在生成任何 `clean_units` 前遇到缺源，只能交空数组和自由形态 `gaps`，无法区分“合法 0 单元”“尚未执行”与“阻塞停止”。
- 状态枚举：局部枚举闭合：`action = retained | moved | merged | reordered`，删除去向为 `appendix | technical-lead | audit | omitted`。缺少角色级运行状态枚举。
- 主要风险：下游仅看到空输出时，无法机械判断是完成、失败还是 blocked，来源整合失败可能被误当作合法空结果继续传递。
- 可声称范围：可声称成功态的来源整合合同足够明确；不可声称该合同已闭合失败/停止数据流。

## 2. skill-mechanism-auditor

- 合同判定：`fail`（候选生产边界清楚；停止路径和整体结果状态缺失）。
- 任务：清楚。虽然角色名叫“机制候选/审计”，实际职责明确是生产可供独立裁判验收的机制候选，不是裁判，也不是最终成文。
- 允许输入：净化正文、source map、关联资产和主控批准的事实证据，足以限制候选来源；不需要完整协议。
- 输出 schema：`mechanism_candidates` 覆盖单一任务、核心判断、输入输出、适用状态/分支、权限/人工门、取舍、反事实、失败/恢复/停止、验证、复用边界和来源；`evidence_gaps` 能记录问题、影响与所需来源。成功态足以交给裁判。
- 禁令：明确不机械凑维度、不写最终文案、不自宣通过、不脱离 source map 发明机制或外部分类，能阻止生产者越权。
- 停止条件：覆盖无法回源、来源冲突、未授权运行代码/外部比较，并禁止用成文掩盖缺口。
- 自足性：正常候选生产路径自足；阻塞路径不自足。schema 没有整体 `status` 或 `blocked_reason`。`evidence_gaps` 能表达“还缺什么”，但不能表达该缺口是否已经触发停止、哪些候选仍有效、是否允许裁判继续。
- 状态枚举：`single_task = mechanism | tradeoff | failure-boundary` 定义清楚；没有候选生产状态或整角色状态。候选数组为空时无法区分“绝对允许 0 条候选”“未运行”和“被证据冲突阻塞”。
- 主要风险：上游证据阻塞可能被裁判误读为“本轮无值得判断的候选”，把运行失败降级成合法 0 条。
- 可声称范围：可声称候选内容 schema 和生产/裁判边界已清楚；不可声称停止状态可无歧义传给独立裁判。

## 3. skill-judge

- 合同判定：`fail`（候选级裁判状态有效；整门与停止状态仍有歧义）。
- 任务：清楚。独立核来源、价值与边界，允许 0 条，只锁定接受项，不生产内容。
- 允许输入：专属规则摘录、Skill rubric、逐 case 回归证据、净化正文、source map、机制候选和已完成事实核查；输入足以执行绝对裁判，也明确不依赖完整生产协议。
- 输出 schema：`verdicts` 给逐候选 verdict、理由、来源检查与回归 flags；`locked_packets` 锁定核心判断、必要证据、页面任务、边界和禁止枝节；`selection_count` 支持合法 0 条。接受项到成文者的交接字段充分。
- 禁令：明确禁止按字段齐全、术语、相对排名或生产成本放行；禁止改候选、补事实、写读者文案和替用户验收，独立性强。
- 停止条件：覆盖 source map / 事实核查不完整、来源不可定位、回归冲突改变门槛和“只有修改候选才能通过”，并要求退回上游。
- 自足性：逐候选正常判定自足；整门失败路径不自足。`blocked` 只存在于单个候选的 `verdict`，没有整门 `status`、全局 `blocked_reason` 或 `return_to`。如果 source map 整体不完整且还不能形成候选 verdict，`selection_count: 0` 会同时像“全部 reject 的合法 0 条”和“整门 blocked”。
- 状态枚举：候选 verdict 的 `accept | reject | blocked` 清楚且与任务一致；缺少整门枚举。`selection_count` 是数量，不是状态，不能替代 `pass | fail | blocked` 或项目另有的权威整门枚举。
- 主要风险：合法 0 条是该合同的重要产品边界，但当前 schema 恰好不能区分“0 条通过”与“裁判没有有效运行”，会破坏这一边界的可审计性。
- 可声称范围：可声称候选级绝对裁判与锁定包职责闭合；不可声称整门结果和停止退回已经结构化闭合。

## 4. skill-writer

- 合同判定：`fail`（成文边界清楚；阻塞和正文不变证明没有结构化出口）。
- 任务：清楚。保持净化正文不变，只把裁判锁定机制写成产品负责人可直接阅读的技术负责人页。
- 允许输入：规则摘录、页面模板、净化正文，以及锁定机制包、必要证据、边界和禁止枝节；没有候选池、裁判讨论或搜索权限，输入最小且足够。
- 输出 schema：`reader_pages` 能交付主读页和技术负责人页引用；`rendered_units` 能把每个锁定项定位到页面区段，并记录因页面负担省略的锁定细节。
- 禁令：明确禁止改题、增加事实、搜索补料、拼落选项和把 AI 解读混入正文；也禁止用标签、时代评价、术语清单或生产过程替代解释。
- 停止条件：覆盖正文/source map 不一致、锁定包缺证据或边界、需要新事实、多个锁定项无法不混题装配四类情况，并要求退回主控。
- 自足性：成功成文路径基本自足；失败路径不自足。schema 没有 `status`、`blocked_reason` 或 `returned_to`，无法表达停止。任务要求“保持净化正文不变”，但输出也没有正文装配校验、所用 clean unit/source map 版本或一致性证据字段；只凭 `main_page_ref` 无法从合同输出确认这一关键承诺。
- 状态枚举：没有角色级状态或单元状态。`omitted_locked_details` 只表达页面负担下的合法省略，不能表达被阻塞、未渲染或失败；空 `rendered_units` 有歧义。
- 主要风险：成文失败可能表现为一个空页面引用；即使成功，也缺少结构化证据证明净化正文未被改写，关键禁令只能靠人工再查。
- 可声称范围：可声称 writer 与候选选择、事实补充和正文轨的权限边界已写清；不可声称其停止状态和“正文不变”承诺已经可由输出 schema 审计。

## 5. cold-start-reproducer

- 合同判定：`pass`。
- 任务：清楚。先做读者页冷读，再对 manifest 声明的最终资产做适用冷启动或复现；两种证据分开记录。
- 允许输入：只有两条规则摘录，以及 manifest 明列的最终读者页、最终资产、测试模式、目标和允许工具；明确排除了生产背景。
- 输出 schema：`reader_cold_read` 记录复述、机制增量、费力点、二次整理与阻塞；`attempt` 记录目标、实际资产、步骤和是否使用禁用背景；`segments` 逐段记录状态、证据与缺口；总结果和 `claim_scope` 能限制声明。正常、失败、阻塞、未运行与不适用都有出口。
- 禁令：禁止读取原 Skill、提示词、日志、候选、裁判理由或口头补充；禁止修文和把好读、局部成功、冷启动或模拟升级为完整复现/真实运行。
- 停止条件：覆盖最终页/资产不完整、输入污染、必须访问禁用背景、未授权写入/付费/敏感操作、测试目标与声明范围不一致；停止时明确标 `blocked`。
- 自足性：通过。合同给出执行顺序、最小输入、禁止背景、输出证据与停止表达，无需完整 Skill 协议即可做一次受限冷启动检查。
- 状态枚举：`reader_cold_read = not-run | pass | fail | blocked`；`segments = not-run | pass | fail | blocked | not-applicable`；总冷启动/复现为 `not-applicable | not-run | pass | fail | blocked`。`reader_cold_read` 不含 `not-applicable` 与“只要有最终读者页就必须先冷读”的任务一致，不构成冲突。连字符写法在本合同内一致。
- 主要风险：未发现会阻断独立执行的 schema 缺口。合同仍不能证明某个具体 manifest 自身完整，但那是运行输入质量，不是本合同缺陷。
- 可声称范围：可声称该合同可以独立执行并准确收窄冷读、冷启动和复现声明；不可据静态合同检查声称任何真实资产已经通过。

## 三、角色独立性检查

### 生产与裁判

- `skill-source-integrator` 只生产一手净化正文与 source map。
- `skill-mechanism-auditor` 只生产机制候选，并明确不得自行宣布通过。
- `skill-judge` 是单独角色，明确不得改候选、补事实或写读者文案。

结论：机制生产者与独立裁判在权限和输入输出上分离，`pass`。角色名 `skill-mechanism-auditor` 容易让人误以为它是裁判，但合同正文已把它限定为“候选生产者”；这是命名理解成本，不是当前职责串位。

### 裁判与成文

- writer 只接收裁判锁定包、必要证据、边界与禁止枝节，不接收“可自由再选”的完整候选池。
- writer 禁止改题、补事实、搜索和复活落选候选。

结论：裁判决定“什么可以写”，writer 只决定锁定内容“怎样自然写出”，权限分离，`pass`。

### 成文与冷读 / 复现

- 冷读角色只接收最终读者页与 manifest 声明资产。
- 它明确禁止读取生产提示、日志、候选、裁判理由和口头解释，也不得替 writer 修文。

结论：成文者与冷读/复现者分离，输入隔离强，`pass`。

### 总拓扑

生产、独立裁判、成文、冷读四类责任没有由同一合同兼任；五任务顺序无悬空生产阶段，也没有裁判后再自由改题的回流。角色**职责独立性通过**。

## 四、状态枚举总检查

### 已闭合的局部枚举

- 来源动作：`retained | moved | merged | reordered`。
- 删除去向：`appendix | technical-lead | audit | omitted`。
- 候选任务：`mechanism | tradeoff | failure-boundary`。
- 候选裁判：`accept | reject | blocked`。
- 冷读：`not-run | pass | fail | blocked`。
- 分段与冷启动/复现：在上列基础上按适用性加入 `not-applicable`。

`accept/reject/blocked` 用于候选去留，`pass/fail/blocked` 用于测试结果，语义层不同，不构成冲突。

### 未闭合的运行级状态

- `skill-source-integrator`：无整体状态。
- `skill-mechanism-auditor`：无整体状态。
- `skill-judge`：只有候选级 verdict，无整门状态。
- `skill-writer`：无整体状态。
- `cold-start-reproducer`：整体状态完整。

四份合同都写了明确停止条件，但前三个生产/裁判合同和 writer 没有与停止条件对应的结构化状态出口。仅靠空数组、`selection_count: 0` 或自由形态 gaps 不能区分 `completed/pass`、合法 0、`not-run` 与 `blocked`。

本次没有读取完整 Skill 协议，因此不替项目发明最终权威枚举；但合同要独立冷启动，至少必须能在自身 schema 中无歧义表达“正常完成、停止阻塞、未运行”及阻塞原因。judge 还必须区分“正常裁判后 0 条接受”与“整门没有有效运行”。

## 五、总判定

- 五任务顺序可重建：`pass`。
- 生产 / 裁判 / 成文 / 冷读职责独立：`pass`。
- 成功路径输入输出衔接：`pass_with_warning`；writer 缺正文不变的结构化证据。
- 停止条件覆盖：文本层面 `pass`。
- 停止条件与输出 schema 闭合：`fail`；前四角色无法无歧义输出整体 blocked / 未运行状态。
- 单合同冷启动自足性：1/5 完整通过；前四份在成功路径可执行，但失败路径需借助合同外约定。
- 整体 verdict：`fail`。

最小结论：这五份合同已经把“谁生产、谁裁判、谁成文、谁冷读”分开，主数据流也可恢复；当前阻断点不是角色串位，而是前四份合同的停止结果没有进入 schema，尤其会把合法 0 条与运行 blocked 混为一谈。静态检查不能据此声称五角色合同已经完整冷启动通过，也不能声称任何真实 Skill 运行或复现通过。
