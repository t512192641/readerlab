## 1. 本文负责什么，不负责什么

本文把 ReaderLab 图书线当前散落在产品决议、工程经验、蓝图、任务卡和运行产物中的信息，整理成一张可供陌生 Agent 理解和讨论的全景图，回答五个问题：

1. 最终产品要解决什么问题；
2. 一篇完整材料进入后，目前依次经过哪些角色；
3. 每个角色负责什么、读取什么、产出什么、调用几次；
4. 当前已经证明什么、最薄弱的地方是什么；
5. 怎样从人工、多会话实验流程走向一个用户可直接调用的 Skill。

本文是派生说明，不拥有新的产品事实，也不是生产 Prompt、任务卡或自动化授权。冲突时按以下 owner 判定：

1. 产品目标与长期责任：[`PRODUCT-DECISIONS.md`](../PRODUCT-DECISIONS.md)
2. 历史失败边界：[`ENGINEERING-LESSONS.md`](../ENGINEERING-LESSONS.md)
3. 长期派生架构：[`blueprints/PIPELINE-MAP.md`](../blueprints/PIPELINE-MAP.md)
4. 单次实验参数：对应 `taskcards/` 任务卡
5. Writer 当前候选约束：[`docs/writer-style-guide.md`](writer-style-guide.md)

[`docs/pipeline-template-draft.md`](pipeline-template-draft.md) 是未来流程草案，其中一些简化尚未获得实验证据，不能把它直接当作当前生产事实。

## 2. 最终目标

### 2.1 产品目标不是“生成摘要”

ReaderLab 图书线服务的是完整阅读：

- 读者先读作者的完整原文单元；
- 只在真正值得停下来的位置看到陪读；
- 陪读引入原文之外、能够独立成立并迁移使用的知识；
- 原文仍然是阅读主轴，AI 不能用总结替代作者；
- 陪读像纸书页边的高手批注，而不是另一篇抢走主线的文章。

一篇合格陪读至少同时做到：

1. 与当前原文的完整论证有真实关系；
2. 带来原文之外的结构性认识；
3. 展示知识的核心命题和运行机制；
4. 能迁移到其他场景；
5. 不伪造来源，不掩盖边界和未知；
6. 用自然中文进入原文，再回到原文；
7. 让读者带走一种以后还能使用的判断方法。

允许一章没有陪读，也允许有多个彼此独立的框架。数量由真实价值决定，不设产量配额。

### 2.2 最终交付形态

图书线的最终读者产物是：

```text
B1：完整作者原文
  +
B2：锚定在相关原文附近的 0-N 条高价值陪读
  +
B3：完成整个声明范围后才允许生成的读薄产物
```

当前 T2.23—T2.25 主要验证了 B1 + B2。B3 尚未成为当前工作重点。

### 2.3 最终 Skill 的目标体验

最终不能要求用户手动创建十几个 Codex 一级会话。理想体验应是：

```text
用户在一个入口提交 EPUB／完整文章并选择阅读范围
  ↓
一个 ReaderLab Skill 建立后台运行
  ↓
内部按角色创建隔离上下文
  ↓
控制层保存冻结文件、状态、哈希和成本
  ↓
只在确实需要产品判断或出现异常时通知用户
  ↓
输出一份可直接阅读、批注和回复的完整章节
```

用户可见的是一个任务、一条进度线和少量判断包；发现者、比较者、来源审核者、Writer 等应是后台功能角色，不应全部暴露成一级聊天。

“角色”描述功能责任，不提前等于一个独立 Skill。最终可以是：

- 一个对用户公开的总 Skill；
- 总 Skill 内部的状态机和控制层；
- 多个不可见或低可见的隔离 worker；
- 确定性工具负责材料、文件、哈希、装配和成本；
- 模型角色只承担确实需要语义判断的工作。

## 3. 当前已验证到哪里

### 3.1 已获得的正向证据

| 证据 | 当前可以声称什么 |
|---|---|
| T2.23，第 19 章端到端通过 | 固定章节上的双陪读可达到产品标准 |
| T2.24，第 16 章端到端通过 | 同一核心责任链在第二个主题不同的章节上成功一次 |
| T2.24 独立比较者 | 比较者能够识别候选之间的支配、互补和薄弱结构 |
| T2.24 Expert 展开 | 两个不同理论对象都能形成独立课程、迁移案例和边界 |
| T2.24 来源审核 | 能发现概念拼接、归属和证据强度问题，并在 Writer 前修正 |
| T2.24 Writer 与忠实性检查 | Writer 可以改善表达，同时由独立角色守住承重语义 |
| T2.25 v06 | “理论可见性”和“理论进入的自然性”能够显著改善最终中文 Reader |
| T2.24 成本台账 | 当前人工端到端流程的模型调用、墙钟和工具成本可以被记录 |

### 3.2 不能外推的结论

当前不能声称：

- 流程已经在大量章节上稳定泛化；
- Writer 风格指南 v1.3 已跨章节验证；
- 候选池能够稳定覆盖不同知识家族和分析层级；
- 当前 Prompt 已成熟；
- 当前人工流程已经适合自动化；
- 独立来源审核可以安全删除；
- P1、P2、P3 可以全部自动化；
- 精确 token 已经可观测；
- 可以直接全书扩产。

### 3.3 T2.25 的真实意义

T2.25 证明的是：

> 在一组已经通过内容层的专家课上，经过多轮产品反馈，可以发现并固化更好的 Writer 表达规则，最终得到发布质量文本。

它还没有证明：

> 一个全新的 Writer 在另一个章节首次读取 v1.3，就能直接产生同等质量。

T2.25 从 v01 迭代到 v06，说明系统具备“可以修到很好”的能力；下一步要验证的是“冻结以后能否第一次就做得足够好”。

## 4. 当前一篇材料进入后的完整流转

### 4.1 当前流程总图

```text
材料进入与完整范围冻结
  ↓
B1 完整作者正文
  ↓
发现 Expert 自主发现 0-N 个候选
  ├─→ 候选池广度旁路诊断（只观察，不反馈生产）
  ↓
独立比较者逐项比较与排序
  ↓
P1：产品负责人判断哪些对象值得展开
  ↓
原 Expert 按候选分支展开完整专家课
  ↓
P2：产品负责人判断这堂课是否值得存在
  ↓
每个对象独立来源审核
  ↓
原 Expert 做必要的最小来源修正
  ↓
原 Expert 选择锚点并冻结承重语义交接包
  ↓
每个对象独立 Writer 编辑
  ↓
每个对象独立忠实性检查
  ↓
确定性装配回完整 B1
  ↓
P3：产品负责人阅读完整章节并验收
  ↓
冻结最终产物、哈希、状态和成本
```

### 4.2 为什么要拆这么多角色

拆分不是为了制造复杂度，而是因为四种责任会互相冲突：

| 责任 | 如果交给同一个上下文，容易出现什么问题 |
|---|---|
| 自主发现 | 一旦提前看到标准答案、产品偏好或历史候选，会变成暗示召回 |
| 候选选择 | 发现者容易承诺自己提出的候选，缺乏淘汰能力 |
| 知识展开与来源纠错 | 审核者若直接重写课程，会把事实核验变成重新选题 |
| Writer 编辑 | Writer 若能新增知识，会在“写顺”时悄悄补造机制和事实 |
| 忠实性判断 | Writer 自审容易把自己的重写理解成忠实 |
| 产品验收 | 技术通过、模型评分和字段完整都不能替代真实阅读体验 |

因此当前采用“角色最小读取闭集 + 冻结文件交接”，而不是把完整历史全部塞给一个模型。

## 5. 每个角色的功能、输入、输出和调用次数

下面描述的是 T2.24 已运行并取得端到端接受的流程。单次任务的候选上限、模型、时间和产品门仍由任务卡拥有，不能自动外推。

### 5.1 控制层／总控

**功能**

- 解析材料并冻结完整阅读范围；
- 为每个角色准备逐文件读取白名单；
- 创建隔离上下文；
- 控制状态晋级和停止；
- 冻结文件与 SHA-256；
- 记录 token、时间、工具和重试；
- 装配产品审阅包；
- 不替 Expert 发现知识，不替产品负责人作价值判词。

**模型调用**

- 材料选择、哈希、装配本身应为 0 次模型调用；
- T2.24 中“同源 Expert 分支派发”额外占了 1 次控制型模型调用，这是当前手工编排成本，不是长期产品必需的语义角色。

**未来优化**

- 将派发、白名单、哈希、状态和通知变成确定性状态机；
- 不再让控制型模型调用承担文件搬运和流程记账。

### 5.2 材料冻结

**输入**

- EPUB、完整文章或其他获准材料；
- 用户指定或任务卡确定的完整作者单元。

**功能**

- 识别完整章节／完整文章；
- 冻结来源、member、scope、正文和哈希；
- 不在确定性选材前读取候选正文；
- 无法确认材料身份时停止。

**输出**

- 材料身份清单；
- 完整 B1；
- 可供模型读取的正文；
- 可供人直接阅读的 Markdown／HTML 版本。

**当前弱点**

- T2.24 的 `chapter-scope.xhtml` 是内部提取片段，不是完整合法 XHTML 文档，直接用浏览器打开会报错；
- 内部冻结格式和人类阅读格式尚未完全分离。

**未来优化**

- 内部保存规范化文本与原始 member 身份；
- 另行生成合法、可直接打开的 Markdown／HTML 审阅版本；
- 两者用内容哈希建立可逆关系。

### 5.3 发现 Expert

**当前调用**

- 每章 1 个全新发现会话；
- T2.24 实际 1 次模型调用。

**输入**

- 完整章节；
- 当前任务卡；
- 产品长期目标和本角色白名单。

**功能**

- 自主发现 0-N 个知识候选；
- 说明候选身份、原文触发和它可能改变的认识；
- 不排序、不写最终 Reader、不联网、不读取历史答案。

**输出**

- 冻结候选池。

**当前合理性**

- “先自由发现，再独立选择”已经优于让模型一步生成成品；
- 保留同一 Expert 继续展开，有利于保存原始发现意图。

**当前弱点**

- 只有一个发现者，候选广度受模型已有知识和章节主题影响；
- 当前发现阶段主要依靠模型参数内知识，无法保证较新的知识进入；
- 两章都暴露出候选容易集中在“机制模型”层的风险。

### 5.4 候选池广度旁路诊断

**当前调用**

- 1 个全新隔离会话；
- T2.24 实际 1 次模型调用。

**输入**

- 完整章节；
- 冻结候选池。

**功能**

- 记录候选涉及多少知识家族；
- 分布在章节哪些位置；
- 属于领域主干、机制模型还是方法实践；
- 是否存在名称不同但实质重复。

**输出**

- 旁路诊断结论。

**隔离要求**

- 不读取比较结果和产品判词；
- 不向本轮生产者反馈；
- 不能推荐正确理论。

**当前状态**

- 它是诊断能力，不是生产角色；
- `pipeline-template-draft.md` 提议砍掉它，但当前候选层级问题尚未解决，暂不应直接删除；
- 未来可以改成控制层的离线评估或抽样审计，不必每章都调用模型。

### 5.5 独立比较者

**当前调用**

- 每章 1 个全新隔离会话；
- T2.24 实际 1 次模型调用。

**输入**

- 完整章节；
- 冻结候选池。

**功能**

- 逐项判断独立学习价值；
- 检查内部组织；
- 检查跨场景迁移；
- 区分候选已有结构和展开时可能补造的结构；
- 判断合理阅读成本；
- 分析候选之间的支配与互补。

**禁止**

- 不增加、改名、合并或展开候选；
- 不读取发现者后续展开；
- 不替产品负责人作最终价值判断。

**输出**

- 比较稿、排序和建议。

**当前状态**

- 这是当前较稳定、证据较强的环节；
- 不能把语义比较伪装成纯确定性规则；
- `pipeline-template-draft.md` 的 P1 自动阈值只是未来提案，尚未证明能替代产品判断。

### 5.6 P1 产品门

**当前次数**

- 每章 1 次产品判断；
- 不计模型调用。

**问题**

> 这个知识对象是否值得投入成本展开？

**为什么放在这里**

- 此时否决成本最低；
- Writer 和来源审核不能救一个不值得存在的选题。

**未来方向**

- 开发阶段继续保留；
- Skill 生产阶段可考虑自动放行低风险明确项、只把 `unknown`、边界冲突和数量过载提交人工；
- 是否完全取消人工 P1 尚未获得证据。

### 5.7 原 Expert 展开

**当前调用**

- 先有 1 次同源分支派发；
- 每个 P1 通过对象 1 次 Expert 展开；
- T2.24 两个对象共 3 次调用。

**输入**

- 完整章节；
- 冻结候选池；
- 中性的获准 candidate ID；
- 不读取比较理由和 P1 产品理由。

**功能**

- 每个分支只教授一个知识对象；
- 形成完整内部结构；
- 给出非本章迁移场景；
- 说明原文案例的真实作用；
- 说明边界和 `unknown`；
- 记录哪些内容来自候选、哪些是本轮新增。

**输出**

- 每对象一份完整 Expert 课；
- 展开新增台账。

**当前状态**

- 这个环节已经在两章多对象上工作；
- 当前主要风险不是能否写长，而是避免为了“完整”现场补造框架形状。

### 5.8 P2 产品门

**当前次数**

- 每章 1 次产品审阅包，可同时判断多个对象；
- 不计模型调用。

**问题**

> 这堂完整课程本身是否值得存在？

**为什么 Writer 前必须判断**

- Writer 只负责表达，不能救课程价值；
- 如果内容层不成立，越往后修成本越高。

**未来方向**

- 第三章前瞻性压力测试继续保留；
- 正式 Skill 是否改为异常升级或抽样复核，需要实验证据；
- 当前不能直接把 P2 删除。

### 5.9 独立来源审核

**当前调用**

- 每个 P2 通过对象 1 个全新审核会话；
- T2.24 两个对象共 2 次模型调用；
- 获得受控的只读联网权限，优先一手和高信任来源。

**输入**

- 对应 Expert 课；
- 不读取其他对象、产品判词或 Writer 稿。

**功能**

- 核验承重主张；
- 判断 `SUPPORTED`、`CORRECTION_NEEDED` 或 `UNKNOWN`；
- 检查理论归属、概念拼接和证据强度；
- 只能确认、收窄或标记未知；
- 不重新设计课程。

**输出**

- 每对象一份来源审核；
- 必要最小修正清单。

**当前合理性**

- T2.24 的两个对象都需要来源修正；
- 它成功拆开了不同理论传统，并把课程自创分类标为“本课综合”；
- 这说明独立来源审核目前仍有真实价值。

**当前争议**

- `pipeline-template-draft.md` 提议把来源审核并入 Expert；
- 该提议尚未通过真实运行；
- 在概念拼接、中高风险事实和陌生理论上，过早合并会失去独立纠错能力。

**建议**

- 下一次压力测试继续保留独立审核；
- 以后再做风险分级：低风险对象可轻审，中高风险对象独立审；
- 不应现在整体删除。

### 5.10 原 Expert 最小来源修正

**当前调用**

- 每个需要修正的对象 1 次；
- T2.24 两个对象都需要修正，共 2 次模型调用。

**输入**

- 自己的 Expert 课；
- 自己的来源审核。

**功能**

- 只改审核指出的问题；
- 不借审核机会重写课程；
- 修正若改变课程核心则停止对象。

**输出**

- 来源修正版 Expert 课，作为 Writer 的唯一语义输入。

**为什么交回原 Expert**

- 来源审核者不拥有课程；
- 原 Expert 最了解哪些修正会动到核心结构。

### 5.11 Expert 交接与承重语义锁

**当前调用**

- 每个来源冻结对象 1 次；
- T2.24 两个对象共 2 次模型调用。

**功能**

- 自主选择一个逐字、唯一、实质相关的原文锚点；
- 指明上下文；
- 列出 Writer 必须保留的变量、机制、因果、边界和证据强度；
- 指明可删除的低收益支线。

**输出**

- Writer 输入包；
- 冻结课路径与哈希；
- 锚点；
- 承重语义锁。

**未来优化**

- 交接包结构稳定后可模板化；
- 路径、哈希和机械字段应由控制层生成；
- 只有锚点与语义锁需要 Expert 判断，没必要让模型重复写文件元数据。

### 5.12 Writer

**当前调用**

- 每个对象 1 个全新隔离会话；
- T2.24 两个对象共 2 次模型调用。

**输入**

- 来源修正版 Expert 课；
- 对应交接包和语义锁；
- Writer 风格指南；
- 不读取完整章节、其他对象、产品判词、来源审核原报告或历史 Reader。

**功能**

- 删除重复和低收益支线；
- 调整顺序；
- 用自然中文解释已有术语；
- 保留理论可见性；
- 让理论从原文困境自然进入，并回到原文；
- 独立呈现“带走什么”；
- 不增加知识、事实、机制、案例、边界或结论。

**输出**

- Reader；
- 编辑台账。

**当前状态**

- Writer 职责边界已较清楚；
- v1.3 已在第 16 章两个不同知识对象上形成通过样张；
- v1.3 只取得下一轮试用资格，尚未跨章节前瞻验证；
- T2.25 从 v01 到 v06 的迭代成本说明“指南能总结经验”，但不证明新 Writer 第一次就能执行好。

### 5.13 独立忠实性检查

**当前调用**

- 每个 Reader 1 个全新隔离会话；
- T2.24 两个对象共 2 次模型调用。

**输入**

- 来源冻结 Expert 课；
- 交接包；
- Reader；
- 编辑台账。

**功能**

- 逐项检查承重语义锁；
- 检查有无新增机制和事实；
- 检查 `unknown` 是否被升级；
- 检查来源强度是否被强化；
- 检查锚点是否保持。

**输出**

- 每对象一份忠实性报告。

**当前状态**

- 这是独立、必要且适合后台并行的环节；
- 未来可把机械项自动化，但语义忠实仍需要模型或可靠语义评估。

### 5.14 确定性装配

**当前调用**

- 0 次模型调用。

**功能**

- 把通过忠实性检查的 Reader 插入唯一锚点之后；
- 不合并独立框架；
- 不修改原文；
- 移除所有陪读后逐字恢复 B1；
- 生成完整章节审阅稿和确定性收据。

**输出**

- 完整 B1 + B2；
- 锚点唯一匹配结果；
- 原文可逆性结果；
- 文件哈希。

**当前状态**

- 这个环节应继续保持确定性，不需要模型自由发挥。

### 5.15 P3 产品门

**当前次数**

- 每章 1 次产品判断；
- 不计模型调用。

**问题**

> 完整章节作为真实阅读体验是否可以接受？

**判断对象**

- 原文完整性；
- 锚点位置；
- 多段陪读是否互补或过载；
- 中文阅读节奏；
- 整体产品体验。

**未来方向**

- 开发阶段必须保留；
- Skill 生产阶段可以默认输出并把低置信异常升级，但不能把技术检查冒充产品接受；
- 是否保留每章人工 P3，应由第三章压力测试后的数据决定。

## 6. 当前实际调用与成本

### 6.1 T2.24 的实际模型调用

两个对象通过 P1 和 P2 时，T2.24 共发生 16 次模型调用：

| 阶段 | 调用数 |
|---|---:|
| 发现 Expert | 1 |
| 候选池广度诊断 | 1 |
| 独立比较者 | 1 |
| 同源 Expert 分支派发 | 1 |
| Expert 展开 | 2 |
| 来源审核 | 2 |
| Expert 最小来源修正 | 2 |
| Expert 交接 | 2 |
| Writer | 2 |
| 忠实性检查 | 2 |
| **总计** | **16** |

另外有：

- P1、P2、P3 三次人工产品门；
- 材料选择、装配和哈希为确定性操作；
- 来源审核发生 3 次工具内重试，没有模型调用重试。

### 6.2 时间

T2.24：

- 模型累计工作时间：约 26.5 分钟；
- 模型关键路径：约 16.7 分钟；
- 正式 run 到 P3 的完整墙钟：约 11.1 小时；
- 完整墙钟主要被人工等待和异步反馈拉长，不等于模型计算时间。

### 6.3 Token

宿主没有为 16 次调用返回 provider usage，也没有可用的获准 tokenizer，因此：

- provider token：`unknown`；
- 可见文本 token：`unknown`；
- 缓存 token：`unknown`；
- 隐藏推理 token：`unknown`。

当前记录是诚实的，但成本可观测性仍不完整。

### 6.4 T2.25 暴露的成本缺口

T2.25 有 v01—v06 多轮产品修订，却没有建立与 T2.24 同等完整的逐调用 usage ledger。因此可以确认最终质量，却不能精确回答：

- 每轮修改用了多少 token；
- 控制层生成审阅包花了多少时间；
- 哪一条 Writer 规则减少了多少返工；
- 如果每章都经历六版，规模化成本会是多少。

下一次实验必须把控制层修改、产品返工和审阅包装配也纳入成本统计。

## 7. 当前方法是否合理

### 7.1 作为研究和验证流程：合理

当前流程的主要优点是：

- 每个失败可以定位到发现、选择、知识、来源、表达或装配中的具体一层；
- 生产者看不到产品答案，保留了真实自主发现；
- Writer 无权救上游选题；
- 来源审核无权重定课程；
- 产品负责人能在昂贵步骤之前否决；
- 原文和中间资产都有身份、哈希和可逆证据；
- 技术通过、语义质量和产品接受没有混为一谈。

这是一套合格的实验 harness。

### 7.2 作为最终生产系统：不合理

当前方式不能直接成为最终产品，原因包括：

- 需要人工创建和管理多个一级会话；
- 角色交接依赖人手整理文件路径；
- 状态、重试和通知没有统一运行时；
- 三个产品门会把真实墙钟拉长；
- 一章两个对象就需要 16 次模型调用；
- token 仍不可精确观测；
- Writer 指南经过同样本多轮修订，存在过拟合风险；
- 候选发现主要依赖模型已有知识；
- 原文内部冻结格式不等于良好的人类阅读界面。

正确方向不是取消隔离，而是把隔离从用户操作迁移到后台编排。

## 8. 当前最薄弱的环节

### 8.1 第一弱点：前瞻性可复现性

当前最大不确定性不是“能否最终修好”，而是：

> 把流程、Prompt 和 Writer v1.3 全部提前冻结后，能否在第三个未动章节不改规则地成功？

T2.25 的六版迭代可能包含同样本过拟合。只有前瞻性运行才能区分稳定规则和针对第 16 章的局部修补。

### 8.2 第二弱点：候选发现的知识层级和新鲜度

当前两章给出的信号是：

- 第 19 章候选家族较窄；
- 第 16 章候选来自多个家族，但仍集中在机制模型层；
- 领域主干和方法实践层的召回仍弱；
- 发现阶段无法保证调用较新的知识。

来源审核只能核实已经发现的候选，不能补回根本没被想到的知识。因此“较新知识进入系统”必须作用于知识供给／发现阶段，而不是只加强末端来源审核。

### 8.3 第三弱点：控制层与用户界面

角色隔离是正确的，用户手动管理隔离是错误的最终形态。

当前缺少：

- 统一 job ID；
- 明确状态机；
- 角色输入包自动构建；
- 后台 worker 生命周期；
- 审批与异常升级接口；
- 结构化产物 registry；
- 精确 usage 接口；
- 单一可读的进度和审阅界面。

### 8.4 第四弱点：成本与产品门

模型关键路径只有十几分钟，但完整墙钟可能跨越数小时。需要区分：

- 模型计算；
- 并行墙钟；
- 工具时间；
- 技术重试；
- 控制层包装；
- 产品等待；
- 产品返工。

未来不能简单以“减少模型调用”为唯一目标；更大的体验问题可能是审批等待、审阅包难读和反复回合。

### 8.5 第五弱点：草案领先于证据

`pipeline-template-draft.md` 已经提出：

- P1 自动化；
- 合并独立来源审核；
- 删除旁路诊断；
- 正式 Skill 取消全部人工门。

这些都是可讨论的未来方案，不是当前已证明事实。特别是 T2.24 两个对象都需要来源修正，说明“立即取消独立来源审核”风险较高。

外部专家讨论时必须把以下三种内容分开：

| 类型 | 例子 |
|---|---|
| 已证明 | 独立比较者有区分力；Writer 与忠实性需要分离 |
| 待验证假设 | 单 Expert 是否足够；v1.3 是否跨章节可用 |
| 未来产品选择 | 是否零人工门；来源审核采用什么风险等级 |

## 9. 下一步：第三个未动章节前瞻性压力测试

下一任务建议暂称 T2.26，但在产品负责人确认方案前不创建任务卡。

### 9.1 唯一实验问题

> 在材料、角色合同、比较标准、来源审核规则和 Writer v1.3 全部提前冻结，且运行中不得修改 Prompt 或指南的条件下，完整流程能否在第三个未动章节产生获接受的端到端样张？

### 9.2 为什么不是继续优化 Prompt

当前已经有足够规则。继续对第 16 章做 Meta Prompt 或句子优化，只会提高同样本表现，不能证明迁移。

下一轮必须把规则当作待检验对象，而不是边跑边改的工具。

### 9.3 运行约束

- 确定性选择一个未动完整章节；
- 不人工挑容易成功的章节；
- 沿用 T2.24 已证明的角色隔离；
- 继续保留独立来源审核；
- Writer 首次前瞻使用 v1.3；
- 候选池广度继续旁路记录，不反馈生产；
- 保留 P1、P2、P3；
- 全程记录控制层、模型、工具、产品等待和返工成本；
- 运行中不得修改 Prompt、指南或评分门救样本；
- 不换章补考；
- 不指定理论；
- 不启动 Skill 或自动化。

### 9.4 终局

| 终局 | 条件 |
|---|---|
| `PROSPECTIVE_TRANSFER_ACCEPTED` | 至少一段陪读全链通过，且无需修改冻结合同 |

- 候选知识家族和分析层级，只作为旁路观察。

## 10. 第三章之后的路线

### 阶段 A：候选池广度与新知识供给专项实验

第三章结束后，把候选发现单独拿出来研究，不能用端到端通过顺带声称候选池问题已经解决。

可比较：

```text
A：模型参数内知识自主发现
B：受控的一手来源／日期化知识库辅助发现
```

需要分别判断：

- 知识家族广度；
- 分析层级广度；
- 较新知识的真实进入；
- 候选与原文的必要关系；
- 牵强候选比例；
- 来源审核成本。

检索增强不能把理论菜单直接塞给发现者，也不能让搜索热度替代自主判断。

### 阶段 B：冻结最小生产合同

在第三章和候选专项实验之后，只固化跨样本稳定的部分：

- 材料身份合同；
- 发现输入输出合同；
- 比较者五项检查；
- Expert 展开和新增台账；
- 来源审核风险等级；
- Writer 语义锁和 v1.x 指南；
- 忠实性合同；
- 装配与可逆性合同；
- usage ledger；
- 错误、停止和零结果合同。

不固化：

- 固定理论名单；
- 固定课程数；
- 固定候选数；
- 固定篇幅；
- 指定正确答案；
- 当前样本特有的句子。

### 阶段 C：后台编排原型

目标是证明不需要用户操作多个一级会话，也能保持相同隔离。

原型至少需要：

1. 单一 job 入口；
2. 状态机；
3. 每角色读取白名单；
4. 后台隔离 worker；
5. 冻结 artifact registry；
6. SHA-256 和可逆性检查；
7. token／时间遥测；
8. P1／P2／P3 或异常升级通知；
9. 可恢复失败状态；
10. 单一连续审阅包。

这个阶段验证的是编排与隔离，不重新发明内容流程。

### 阶段 D：ReaderLab Skill v0.1

建议最终采用“一个公开 Skill + 内部角色”的形态，而不是十几个用户可见 Skill。

可能的内部结构：

```text
ReaderLab Skill
├─ intake：材料识别与冻结
├─ orchestrator：状态、白名单、并行和停止
├─ discovery worker
├─ comparison worker
├─ expert workers
├─ source-audit workers
├─ writer workers
├─ fidelity workers
├─ assembler
├─ usage recorder
└─ review presenter
```

内部模块可以是 Prompt、私有子 Skill、Agent 配置或确定性代码；在编排实验之前不提前决定。

### 阶段 E：人工流程与 Skill 影子回归

Skill v0.1 不应直接扩产。先做：

- 已接受章节的确定性回归；
- 一个新章节的人工流程与 Skill 流程对照；
- 检查候选、内容、来源、Writer、锚点和装配；
- 检查隔离是否真实；
- 比较调用、token、墙钟和产品返工；
- 检查用户是否只需面对一个任务。

只有 Skill 输出与人工已验证流程在关键合同上等价，才进入小规模生产。

### 阶段 F：小规模扩产与透镜治理

逐步扩大章节数量，同时记录：

- 哪些知识对象重复出现；
- 哪些临时 Expert 值得晋升为正式透镜；
- 哪些透镜持续失败或被质疑；
- 每个版本的使用结果；
- 人工复盘后的升降和退役。

正式透镜不能被静默覆盖或删除。

## 11. Meta Prompt 应该放在哪里

Meta Prompt 不是当前下一步。

它适合在最小合同已经跨样本稳定后，用于：

- 生成角色 Prompt 候选；
- 检查 Prompt 是否遗漏输入、输出和停止条件；
- 生成不同措辞版本做回归；
- 减少维护成本。

它不能：

- 自己决定产品目标；
- 自己证明生成的 Prompt 更好；
- 用模型评分替代产品判词；
- 在生产运行中动态改 Prompt 救样本；
- 把历史正确答案注入发现者。

Meta Prompt 产出的任何版本都必须经过冻结样本和未知样本验证。
