# ReaderLab 当前实现忠实性审查说明

## 审查目标

本次审查不是代码风格、命名、格式或一般工程整洁度审查。核心问题是：

> 当前实际运行是否忠实实现了 ReaderLab 已确认的产品要求；技术检查通过的对象，是否真的交付了
> 产品负责人要的“借完整外部认知框架读厚原文”。

本轮只冻结和暴露当前事实，不修改代码、Prompt、方法、schema、合同或语义产物。审查者应把
`implemented`、`integrated`、`verified` 与 `accepted` 分开，不把文件存在、技术 `PASS`、
模型评分或流程跑通当成产品接受。

## 产品负责人当前观察

产品负责人对当前成品提出以下问题：

1. C 的理论内容没有解释清楚；
2. C 的框架内部结构没有真正搭建；
3. 正文主要在解释 A 为什么可以连接到 C，而不是先把 C 本身教清楚；
4. `M1 / M2 / M3` 标签与实际交付深度可能不一致；
5. 技术审核通过，但产品负责人不接受实际成品。

这些是本次 Code Review 要核对的产品观察，不应被现有六条 `TECH_PASS` 预先否定。

## 希望审查者重点判断

1. U01／U02／U03 的六条成品是否先独立建立了 C 的问题、核心概念、内部关系、机制、边界与可迁移
   判断，再回到 A；还是主要完成了 A → C 的连接说明。
2. 删除 A 与原文连接段后，读者是否仍能从正文中学会一套可独立使用的 C；若不能，H4
   “外部知识承重”是否被判得过宽。
3. 六条 `M1 / M2 / M3` 标签是否有可复验定义和正文证据；特别是 D-U01、D-U02 的
   `M1+M2+M3` 是否真的交付了相应层级。
4. 当前 H1—H10 技术 rubric 是否漏掉“框架内部结构完整度”“教学展开深度”“标签—正文一致性”
   等关键产品要求。
5. 把搜索 C、选择 C、恢复 C、Writer 写作和深度自标合并到同一会话，是否造成自证循环，使后置
   技术审核只能核对来源与连接，不能发现知识结构没有真正恢复。
6. U pilot 与现行 `BOOK-CONTENT-FLOW-v2` 的 Expert → 内容锁 → Writer → Fidelity 责任 seam
   相比，哪些省略是实验允许的简化，哪些已经改变了产品对象。
7. T2.35 → Writer sidecar 为什么能在锁定语义与 Fidelity 技术通过后仍停在 P3 未接受；当前
   Fidelity 是否只检查“Writer 没改坏”，却没有检查“上游课程和最终阅读体验值得存在”。
8. 当前实际入口、模型、Prompt、schema、日志和产品状态能否由仓库独立还原；哪些关键事实仍只靠
   runner 自报或仓库外文件。
9. `tools/run.py`、项目 Skill 和各 sidecar 之间是否存在一个真实 orchestrator；若没有，当前
   “runtime”应如何准确描述，避免把人工多会话实验误称为已集成生产链。
10. 技术审核通过而产品不接受时，失败应归因到 Discovery、C 恢复、Expert、Writer、Fidelity、
    产品 rubric，还是责任合并本身；请以现有产物给出证据，不为缺失步骤补故事。
