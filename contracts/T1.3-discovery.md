# T1.3 发现合同

## 1. 责任

发现以 B1 一手正文为对象，只提出“哪里值得进一步探索、为什么、希望获得哪类增量”的透视需求。透视需求是问题入口，不是答案、专家创建或调用、知识卡、审核结论或产品判词。

本合同只使用 B1 的产品责任作为概念性上游，不依赖 T1.2 已生成合同，也不预设 B1 的具体字段或锚点实现。

## 2. 透视需求的最小结构

每条非空透视需求只要求以下三个字段：

| 字段 | 最小含义 |
|---|---|
| 位置锚点 | 把需求关联到其所回应的 B1 原文位置，使后续环节能够核对“为什么在这里停下”。定位粒度、编码方式和精确接口尚未冻结。 |
| 为什么值得停下 | 明确承载一个清楚、单一、值得深入的问题，并说明回答它会增加哪一种理解或判断价值；不能只写“重要”“有意思”“值得看看”等笼统理由，也不提前给出知识答案。 |
| 期望增量类型 | 说明希望探索带来哪种认知增量形态。所有八类合法增量都可作为期望形态，不得因发现方式、透镜或诊断手段而收窄。 |

这三个字段是发现输出的最小责任，不是对 Markdown、JSON、数据库或其他 schema 的冻结；字段的机器表示、必填编码、基数与组合方式留待真实入口和后续调用合同决定。

每条需求只承载一个主要问题。若同一位置存在多个彼此独立的问题，应分别判断是否各自值得提出，不能把它们拼成一个含混需求；问题无法被清楚、单一地表达时，该项不得交给下游。

## 3. 期望增量类型保持开放

以下八类均为合法的期望增量形态，地位相同，任何一类都不得被排除：

1. 机制
2. 模型
3. 方法
4. 预测
5. 权衡
6. 可迁移关系
7. 高手指点
8. 跨行业视角

类型只表达希望增加的认识形态，不自动证明需求值得承接，也不自动证明未来内容语义合格或获得产品接受。发现不得把合法增量收窄为“新机制”“新关系”或其他子集。

## 4. 承接次序与零发现

- 能由可复用的正式透镜承接真实需求时，优先正式透镜。
- 只有正式透镜不能承接的真实缺口，才可提出由本材料、一次运行范围内的临时专家承接；发现不创建或调用临时专家。
- 每次执行发现都必须完成一次受控偶遇探索，不能因已有候选、时间便利或预期零结果而跳过；该探索的具体模型、Prompt、调用方式、完成证据字段与 schema 尚未冻结。
- 强制的是完成探索，不是产出内容。受控偶遇探索完成后允许零发现，不承担非零交付责任。
- 发现数量不设配额。没有值得深入的需求时，零发现是合法输出；不得为了非零、数量、覆盖面或形式完整而凑数。
- 零发现只表示本次发现输出为空，不自动证明语义质量或产品通过。

## 5. 职责边界

发现止于提出透视需求，不执行或替代以下责任：

- 正式透镜、临时专家或其他专家的创建或调用；
- 知识卡生成；
- 独立审核、锁定或淘汰；
- Writer 表达或 B2 组装；
- 语义验收或产品负责人判词。

本合同不冻结发现模型、Prompt、调用合同、阈值、发现数量、探索线索 schema、调用提案 schema、正式透镜的发现／晋升合同，也不冻结 `tandem-comments` 的精确接口（包括锚点格式）。上述实现细节不能从三字段反推。

## 6. 缺口与决策归属

不涉及产品判断的纯技术缺口由主控技术门处理，并保持对产品负责人可见；在技术门明确前维持 `unknown`，不得由本合同猜测冻结。

未完成一次受控偶遇探索，或任一非空透视需求没有在“为什么值得停下”中承载清楚、单一、值得深入的问题，均构成技术阻塞；该次发现不得交给知识探索环。阻塞不能靠凑出需求解除。

若后续执行遇到产品判断、材料授权、新产品事实或产品决议冲突，必须停止并交由产品负责人决定；技术门、发现模型或下游环节不得代替该决定。
