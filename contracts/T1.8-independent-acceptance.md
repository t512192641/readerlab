# T1.8 冻结后独立验收合同

## 1. 合同目的与适用边界

本合同定义图书线生产产物冻结后的独立验收边界、五项语义标准和三层报告。它只规定长期必须保留的判断语义，不规定某次运行的数值门槛、聚合办法、裁判配置或产品通过线。

本合同已由 M1 在语义不变前提下冻结为 `frozen`。它不执行 T2.2，不提供或读取考卷样张、答案、金标、反例判词、裁判材料或评分表；该冻结不建立 runtime `integrated`、资格通过、semantic／product 合格或 `accepted`。

## 2. 冻结前置与生产／验收隔离

### 2.1 唯一合法时序

独立验收只能在生产产物冻结之后开始。开始验收前，execution 层必须能够核对：

- 本次生产产物的固定对象与声明范围；
- 能唯一识别该冻结版本的身份和冻结证据；
- 每个实际验收对象与一个既有冻结 B2 单元一一对应，并保留该单元的 `b2-item-id`、冻结生产产物可信身份及内容 hash、固定 scope／范围；
- 验收读取的是该冻结版本，而不是可继续改写的生产中间态；
- 生产冻结发生在任何独立验收判断之前。

任一前置无法核对时，验收不得开始：execution 记录“冻结前置未满足”或 `unknown`，semantic 与 product 均保持 `unknown`。这是一项隔离硬阻塞，不是语义失败处理规则。

### 2.2 生产端禁止读取

生产端不得读取、接收或根据以下信息调整生产产物：

- 本次验收答案或预期结论；
- `GOLD-STANDARDS.md`、`examples/` 及其金标、样张、标签和产品判词；
- 本次运行之外的产物与验收结论；
- 裁判答案、裁判材料或裁判预测；
- 五项评分表、评分说明、评分 key 或其他可泄露验收结论的材料。

生产端可以依据正向产品目标开放探索，但不得借验收答案反向生成。流程、角色或目录如何实现隔离由后续执行合同决定；无论采用何种实现，上述信息边界都必须成立。

### 2.3 独立验收端允许读取

独立验收端只可读取当前验收任务逐项授权的材料。最低需要冻结生产产物、对应原文和冻结范围；金标、正反例或其他裁判材料只有被当前任务逐文件授权时才可读取。读取例外不得传回生产端，也不得跨任务、跨运行或跨会话继承。

任务中的逐文件读取授权只界定验收上下文，不能替代材料本身的来源、版权或使用授权。材料授权必须由产品负责人明确决定；缺少该决定时不得读取或验收相应材料。

独立验收不得修改被验收的冻结生产产物。验收执行者、模型、会话、Prompt、人数和组织方式尚未冻结，但其上下文必须与生产答案隔离。

## 3. 验收对象与记录原则

semantic 层对冻结范围内的每个实际验收对象分别判断。每个对象必须一一对应一个既有冻结 B2 单元，并原样保留以下共同身份：

1. 该单元既有的 `b2-item-id`；
2. 该单元所在冻结生产产物的可信身份及内容 hash；
3. 验收与判词适用的固定 scope／范围。

`b2-item-id` 不能单独替代冻结产物身份、内容 hash 或 scope。验收端不得把一个冻结 B2 单元拆成多个对象、把多个单元合成一个对象，或先改写标题、正文、位置及其他内容再换成新的验收对象。`execution`、`semantic` 与 `product` 必须引用上述同一个固定对象身份，不能各自重建、缩写或换写对象。

对象还必须能指出其所回应的原文位置。具体锚点格式，以及验收／判词记录的文件路径、schema 与编码方式尚未冻结。

每个对象都必须完整保留下列五项语义，不得删项、合并成单一分数或用其中一项代写其他项：

1. 内容增量；
2. 解释深度；
3. 原文关联；
4. 认知杠杆；
5. 呈现质量。

每项记录都应包含：定性判断、支持该判断的对象内证据、对应原文证据、判断理由和证据边界。这里固定的是信息责任，不是最终机器字段名、类型或 schema。

`unknown` 表示现有固定证据不足以作出该项定性判断。它不是合格，也不是不合格，更不能被机器自动改写为任何产品判词。

## 4. 五项语义标准与定性判断语言

### 4.1 内容增量

判断问题：这条内容是否让读者得到原文没有直接给出的具体认识，而不只是复述、整理、换名、同义改写或通用提醒？

合格方向可以表现为机制、模型、方法、预测、权衡、可迁移关系、高手指点、跨行业视角或其他受证据支持的真实增量；不要求固定类型，也不要求每处都必须生成内容。

定性判断必须使用以下一种语言，并说明具体新增了什么或为何没有新增：

- `有实质增量`：能明确指出原文之外、且受证据支持的具体认识；
- `无实质增量`：实质仍停留在原文复述、整理、换名、明显改写或空泛提醒；
- `unknown`：固定证据不足，无法判断是否形成实质增量。

### 4.2 解释深度

判断问题：这条内容是否把承重判断讲透，使读者理解“如何发生、为何成立、在什么条件和边界下成立”，而不只是给结论、列概念或堆信息？

深度由问题本身所需的解释责任决定，不由篇幅、术语数量或背景声望替代。

定性判断必须使用以下一种语言，并指出解释链成立或断裂的位置：

- `解释充分`：关键关系、原因、条件或边界已被讲清，足以支撑承重判断；
- `解释不足`：承重判断缺少必要解释，或以断言、术语和信息堆叠代替解释；
- `unknown`：固定证据不足，无法判断解释是否充分。

### 4.3 原文关联

判断问题：这条内容是否准确回应可追溯的原文位置，并帮助理解该处，而不是脱离原文自说自话、误读作者或把无关知识贴在附近？

关联成立要求判断对象、对应原文和解释关系可以被核对；它不预先冻结锚点字段或定位粒度。

定性判断必须使用以下一种语言，并指出关联所依赖的原文证据：

- `关联成立`：对象与原文位置可追溯，解释确实回应该处且没有扭曲其含义；
- `关联不成立`：对象无法可靠回到原文，或虽相邻却没有回应、偏离或扭曲该处；
- `unknown`：固定证据不足，无法判断关联是否成立。

### 4.4 认知杠杆

判断问题：读者看完后是否获得了一个具体的理解或判断抓手，能够更好地解释、辨别、预测、权衡或迁移，而不只是“知道多了一点信息”？

判断理由必须说清：如果删掉这条，读者会失去哪一种具体理解或判断能力。答不出这一点，不能仅凭新奇、正确或信息丰富声称形成认知杠杆。

定性判断必须使用以下一种语言，并写明获得或缺失的判断能力：

- `形成认知杠杆`：能指出读者新增的具体、可复用理解或判断能力；
- `未形成认知杠杆`：内容没有改变读者可用的理解或判断能力；
- `unknown`：固定证据不足，无法判断是否形成认知杠杆。

### 4.5 呈现质量

判断问题：表达是否让承重内容清楚、连贯、可读，并与原文附近的阅读过程相容，而不是因含混、跳跃、拼贴、字段堆砌或不必要负担妨碍理解？

呈现质量独立于内容增量：表达顺畅不能挽救没有价值的内容，有价值的内容也不能免除可读性判断。数量、长度和风格不得替代对实际理解效果的定性判断。

定性判断必须使用以下一种语言，并指出表达如何帮助或妨碍理解：

- `呈现清楚`：组织与措辞服务于一条可跟随的解释线，读者能够把握承重内容；
- `呈现妨碍理解`：表达结构或措辞造成实质理解障碍；
- `unknown`：固定证据不足，无法判断呈现是否清楚。

## 5. 五项整体保留与非聚合边界

- semantic 报告必须逐对象、逐项原样记录五项判断；不得只保留总评。
- 一项的正向判断不得覆盖、抹除或改写另一项的负向判断或 `unknown`。
- 不同验收对象之间也必须保留各自结论；是否允许以及如何处理跨项抵消仍为 `unknown`，本合同不据此计算整体合格。
- 本合同不定义总分、平均分、权重、排序、通过比例、最少条数或其他聚合公式。
- semantic 可以对固定对象作五项定性判断，但不得把未冻结的聚合办法伪装成评分 gate。

## 6. 三层报告合同

验收报告必须严格分为 `execution`、`semantic`、`product` 三层。三层必须共用同一固定对象身份，但不得互相代写结论。

### 6.1 execution

只记录确定性执行事实，至少包括：

- 被验收对象与声明范围；
- 每个对象与既有冻结 B2 单元的一一对应，以及原样保留的 `b2-item-id`、冻结生产产物可信身份及内容 hash、固定 scope／范围；
- 生产冻结证据及其先于验收判断的证据；
- 实际验收输入与读取授权；
- 生产／验收隔离检查结果；
- 报告产物的身份与执行结果；
- 无法核对的事实及其 `unknown`。

execution 结论只能说明文件、身份、范围、隔离或流程是否按合同成立，不能推出 semantic 合格或 product 接受。

### 6.2 semantic

只记录固定对象在本合同下的语义判断，至少包括：

- 每个对象的可追溯位置；
- 与 execution 完全相同的固定对象身份；
- 内容增量的定性判断、证据、理由和边界；
- 解释深度的定性判断、证据、理由和边界；
- 原文关联的定性判断、证据、理由和边界；
- 认知杠杆的定性判断、证据、理由和边界；
- 呈现质量的定性判断、证据、理由和边界；
- 五项未聚合的并列摘要，以及所有 `unknown`。

semantic 判断属于独立验收证据，不是产品判词。裁判、模型、机器或技术负责人即使形成一致判断，也只能写在 execution 或 semantic 的相应责任范围内。

### 6.3 product

product 只记录产品负责人对同一固定对象与范围作出的明确产品判词及其适用边界。每条判词记录必须绑定与 execution、semantic 完全相同的 `b2-item-id`、冻结生产产物可信身份及内容 hash、固定 scope／范围，并绑定产品负责人给出的以下四级标签之一：

- `惊艳`
- `有用`
- `平庸`
- `废弃`

未取得产品负责人对该固定对象的直接四级标签时必须写 `unknown`。生产 B2 单元内的 `product-value-label` 必须继续保持 `unknown`；判词只能进入独立、不可变的验收／判词记录，不得写回或覆盖冻结生产产物。该记录的具体文件路径、schema 和编码方式均为 `unknown`。

judge、模型、机器、自动评分、流程结果和技术负责人意见均不得填写、推定、代签或替代 product 判词。产品负责人可以参考 execution 与 semantic，但只有产品负责人能够决定是否接受；产品接受也不能倒推缺失的 execution 或 semantic 证据已经存在。

## 7. 三类事实都不得自动通过

- `流程跑通`：只能形成 execution 证据，不能自动判 semantic 合格或 product 接受。
- `互动可用`：只能说明相应交互能够使用，不能自动判 semantic 合格或 product 接受。
- `零条结果`：只能说明固定范围内的结果数量为零；它既不能自动合格，也不能自动不合格，更不能自动成为 product 判词。

零条结果时仍须如实报告 execution 事实、可判断的 semantic 范围和 product 权属；后续如何处置不由本合同提前决定。

## 8. 尚未冻结的事项

以下事项当前统一为 `unknown`，不得从历史参数、一次运行、模型输出或本合同中的定性语言推导为定案：

- 五项在未来机器实现中的精确字段名、字段类型和 schema；
- 任何数值阈值、分数、权重、比例或数量门槛；
- 五项之间或多个对象之间的聚合公式；
- 跨项抵消是否允许以及如何处理；
- 任一负向判断、`unknown` 或零条结果的失败处理；
- 裁判人数、角色组合、模型、Prompt、调用粒度与组织方式；
- 自动评分办法、评分 gate 与最终通过线；
- 资格考试样本、答案、计分和 T2.2 的执行细节；
- 验收／判词记录的具体文件路径、schema 与编码方式。

这些事项只有在相应后续任务获得所需授权和证据后才能另行决定。产品事实或产品通过线若需改变，只能由产品负责人决定。

## 9. 缺口与权属升级

- 发现纯技术缺口时，必须在 execution 中记录缺口、影响范围和 `unknown`，提交主控技术门处理，并让产品负责人能够看到该缺口及处理状态。主控技术门可以处理技术方案，不能借此给出产品判词或改变产品事实。
- 实际验收对象无法与既有冻结 B2 单元一一对应，完整固定身份缺失或三层身份不一致，以及发生拆分、合并、内容换写或生产标签位被写入，均属于验收开始前的技术阻塞；semantic 与 product 保持 `unknown`。
- 需要产品判断、材料授权、产品事实，或 owner 文档与派生内容发生决议冲突时，必须停止相关判断并记录 `unknown`；只有产品负责人能够作出决定。judge、模型、机器、技术负责人和主控技术门均不得替代。

上述升级边界不定义语义负向判断或零条结果的失败处理；这类处理仍属于第 8 节的未冻结事项。

## 10. 状态与后续边界

本合同已由 M1 独立 gate 在语义不变前提下冻结为 `frozen`、`long-term`。M1 冻结只固定本合同身份与既有语义；不运行独立验收、不执行 T2.2、不读取考卷样张、不收集产品判词，也不建立 runtime `integrated`、资格通过、semantic／product 合格或 `accepted`。
