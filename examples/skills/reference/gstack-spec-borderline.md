# gstack/spec 主流程迷你成品页

## 页首标识

- Skill 名：`gstack/spec`
- 材料身份：`gstack/spec` 的冻结讲解样张；本文件已经自包含，不依赖原 Skill 目录。
- 本单元位置：`/spec` 是 gstack 工作流里的“把模糊意图变成 backlog-ready spec”的入口。它位于实现之前，负责把用户一句话变成陌生执行者也能接手的任务。

## 这是正文：净化后的主流程

`/spec` 被触发时，不允许立刻写 issue。它先追问五件事：

1. 谁会被影响？
2. 现在实际发生了什么？
3. 应该变成什么样？
4. 为什么现在要做？
5. 怎样算完成？

五问闭合后，它继续锁边界：哪些明确不做、会碰到哪些系统、是否有先后顺序、最小版本是什么、做错了怎么回滚。

接着进入技术追问，但这里有一个硬要求：问技术问题前，必须先读至少一个仓库证据。它不能把通用 checklist 丢给用户，而要先看文件、目录、配置或现有文档，再基于证据问剩下的问题。

之后它产出完整草稿，让用户确认“这是不是你想要的”。确认后才进入质量门：先做语义内容审查，再做确定性脱敏扫描，最后让另一个模型按“陌生执行者是否能执行”打分。通过后才归档、发 GitHub issue，必要时再创建新 worktree 并派生执行 agent。

## 这是产品解读：它到底帮用户解决什么

这个 Skill 不是“帮你写一张漂亮工单”，而是防止 AI 过早把模糊愿望包装成任务。

普通 agent 很容易在第一轮就给方案：标题很完整、分点很漂亮，但真正执行时会发现范围、验收、边界、现状都没锁住。`/spec` 的价值是把“看起来像需求”的东西先过一遍闸门，只让可执行的东西进入 backlog。

它牺牲了速度。用户会多回答几轮问题，agent 也要先读仓库证据。但换来的结果是：执行者打开 issue 后，知道为什么做、改哪里、怎么验收、哪些不要碰、失败怎么退。

## 这是技术解读：为什么它设计得这么重

从产品负责人视角看，`/spec` 有几段看起来很啰嗦：启动状态探测、AskUserQuestion 兼容、脱敏扫描、归档、dirty worktree 检查、worktree 派生。这些不是阅读主体，但它们解释了这个 Skill 为什么能在真实开发环境里少出事故。

第一层重，是“先问清楚再写”。它把需求澄清拆成 Why、边界、证据、草稿确认四段，避免 agent 靠气氛补全用户没有说的话。

第二层重，是“先读证据再问技术问题”。这相当于要求 agent 先做一点功课。用户不需要从零讲项目结构，agent 也不能假装自己懂。

第三层重，是“发出去之前扫描”。语义审查负责看正则抓不到的风险，例如把真实人名和负面判断绑在一起；确定性扫描负责抓密钥、PII、内部策略等更硬的风险。这个设计的核心不是信任某一个模型，而是把可能公开传播的文本当成危险出口，临门再扫一次。

第四层重，是“执行前保护现场”。如果当前 worktree 有未提交修改，直接派生 agent 可能让它看见不该看的半成品，或者基于脏状态工作。`/spec` 因此要求在 spawn 前确认：继续、stash，还是取消。

换成非工程语言：`/spec` 像一个严格的项目秘书。它先逼你把事说清，再查一下现场，再写成任务，再做保密检查，最后才把任务交给别人。它慢，但慢在防止后面更贵的返工。

## 读完带走

- `/spec` 的核心不是 issue 模板，而是“模糊意图进入执行前的闸门”。
- 它最值得继承的做法是：五问锁 Why、边界先行、读证据后再问、草稿确认、出口扫描、执行前保护现场。
- 它最不适合照搬的部分是大段宿主兼容和 telemetry 外壳。ReaderLab 主读页应剥离这些噪声；技术负责人页只解释它们为什么存在。
